## 결론
- 패키지 방향은 v0과 같습니다. 설정 생성기가 아니라 운영 패키지이고, 채널 레이어는 직접 만들지 않습니다. 리뷰어도 이 방향에는 동의했습니다.
- **v0.1의 범위는 줄입니다.** 부팅 가드의 "자동 최신본 판정·자동 격리"를 빼고 **진단 + 모호하면 기동 거부 + 명시적 복원**으로 바꿉니다. 리뷰의 must-fix 1·2를 받아들였습니다.
- v0에서 내가 틀린 주장 셋을 정정합니다(아래 2절). 그중 하나는 재측정으로 확인했습니다.

## 1. 리뷰로 바뀐 점 (근거를 직접 확인한 것만)

### 1-1. 부팅 가드(guard.py)는 공개 기능으로 쓰기에 불안전 — 받아들임 (must-fix)
직접 확인한 코드(`spikes/litestream/docker/guard.py`):
- **원격 조회 실패와 빈 목록을 둘 다 "로컬 유지, exit 0"으로 처리합니다**(:19-22). S3가 끊긴 동안 옛 볼륨이 부팅하면 검증 없이 서비스를 시작하고, 복제가 다시 붙을 때 최신 이력을 덮을 수 있습니다. 2부 D2에서 본 "S3 단절 중에도 앱은 정상"이라는 성질과 맞물리는 위험입니다.
- **메타 디렉터리가 없으면 원격으로 복원합니다**(:34 `local is None`). `litestream reset`, 메타를 다른 볼륨에 둔 경우, `meta-dir` 지정처럼 정상 운영에서도 메타가 없을 수 있습니다. 이때 **더 새로운 로컬 DB를 버리는 쪽**으로 갑니다.
- DB 파일 내용과 메타의 일치를 검사하지 않습니다. 비교하는 건 파일명의 숫자뿐입니다.
- 격리는 `db.name + "*"`를 여러 번 rename하는 방식이라, 중간에 죽으면 반쯤 옮겨진 상태가 남습니다.
- `litestream ltx` 기본값은 L0만 나열합니다(`-level` 기본 0, `ltx -h`로 확인).

**v1 설계:**
- 상태를 셋으로 판정합니다: `fresh`(로컬 DB 없음 → 복원), `match`(로컬과 원격이 같은 이력 → 기동), `unknown`(조회 실패, 메타 없음, 원격이 앞섬, 판정 불가).
- **`unknown`이면 기본은 기동 거부(exit ≠ 0)입니다.** 운영자가 `sqlite_restore --force`나 `--keep-local`로 명시해야 진행합니다.
- 자동 격리·복원은 0.1에 넣지 않습니다. 넣더라도 "같은 이력임을 증명한 경우"로 한정하고, 그 증명 방법은 [확인 필요]입니다. 예를 들어 복원본과 로컬의 같은 TXID 지점 페이지 해시를 비교하는 방안이 있습니다.
- D4 "가드 통과"는 **순차 전환 1가지 경우**의 결과로만 적고, 공개 기능의 근거로 쓰지 않습니다.

### 1-2. `sqlite_serve`를 Django 관리 명령으로 두면 순서가 깨짐 — 받아들임 (must-fix)
- Django 관리 명령은 `django.setup()`과 system checks를 거친 뒤에야 `handle()`에 들어옵니다. 그 사이에 DB를 여는 코드(앱 ready, 체크)가 있으면, **복원 전에 빈 DB 파일이 생깁니다.** 그러면 `-if-db-not-exists`가 "DB가 이미 있다"고 보고 복원을 건너뜁니다.
- v1 설계: 복원 전 단계(guard → restore)는 **Django를 import하지 않는 독립 CLI**(`python -m <pkg>.boot`)로 둡니다. migrate와 서버 실행만 그 뒤에 Django로 넘깁니다.
- 리뷰어 지적대로 랩 엔트리포인트는 `gunicorn config.wsgi`(WSGI)였습니다. wireview는 ASGI이므로 serve는 uvicorn/daphne 명령 전달과 종료 신호를 **ASGI로 다시 검증**해야 합니다(미검증).

### 1-3. "복제 지연 = 최신 LTX 시각"은 틀린 정의 — 받아들임
- 쓰기가 없는 정상 DB도 마지막 업로드 시각은 오래됩니다.
- v1: 헬스 상태를 `caught_up / backlog / unknown` + 관측 시각으로 나눕니다. `backlog`는 로컬에 쓰기가 진행 중인데 원격 TXID가 N분째 그대로인 경우입니다. "복구 가능성"은 헬스에서 말하지 않고, 주기적 복원 검증(별도 작업)으로 확인합니다.

### 1-4. VFS `CONN_MAX_AGE=None` 강제 — 받아들임(일부)
- D5는 WSGI(gunicorn)에서 잰 결과입니다. ASGI에서 Django의 영속 연결은 동작이 다르고, 공식 문서도 async 환경에서는 영속 연결을 권하지 않습니다([확인 필요]: 6.1 문서의 정확한 문구).
- v1: VFS 라우터는 2단계로 미루고, "강제 체크"가 아니라 "WSGI에서는 `None` 필수"라는 문서 경고로 둡니다. ASGI 조합은 미검증으로 표기합니다.
- `sqlite3_reset_auto_extension()` 우회는 **Litestream 것만이 아니라 프로세스의 모든 자동 확장을 해제합니다**(SQLite C API 의미 그대로). 라이브러리 기본 동작으로는 넣지 않고, 사용자가 켜는 옵션으로만 둡니다.

### 1-5. 시스템 체크 재분류 — 받아들임
- **정적 체크**(설정만 봄, DB를 열지 않음): `transaction_mode`가 IMMEDIATE가 아님 → Warning. `timeout` 미명시는 경고하지 않습니다(Python 기본값이 5초). VFS 별칭 + WSGI 경고.
- **opt-in 진단**(`manage.py sqlite_doctor`, 실제로 연결함): 실제 `journal_mode`, `busy_timeout`, SQLite 버전, 마운트 종류(알 수 없으면 `unknown`), Litestream 설정 파일 구문과 DB 매핑.
- **뺀 항목**:
  - "InMemory 레이어인데 프로세스가 여럿": check 시점에는 프로세스 수를 알 수 없습니다. wireview W006(`checks.py:502`)이 이미 문자열로 경고하므로 중복입니다.
  - NATS 토큰 체크: `connect_options`로도 인증을 넣을 수 있어 오탐이 납니다(`channels_nats/layer.py:215`).
  - "SQLite 버전 하한": Django가 이미 3.37 하한을 검사합니다.

## 2. v0에서 틀린 주장 정정

### 2-1. "폴링 지연 50ms는 튜닝으로 없어지지 않는 구조적 하한" → 틀림 (재측정으로 확인)
channels-lite ORM, 1:1 지연과 유휴 수신자 1개의 10초 CPU를 쟀습니다. 로그: `runs/radar-spike-sqlite-layer-20261007-161819/verify2.log` 4차.
- `polling_interval` 0.1초: p50 50.9ms, 유휴 CPU 59ms/10초
- 0.02초: p50 12.5ms, 유휴 CPU 181ms/10초
- 0.005초: p50 4.5ms, 유휴 CPU 637ms/10초
- 0.001초: p50 2.3ms, 유휴 CPU 1,916ms/10초 (코어의 약 19%)

정정한 결론: 지연은 폴링 간격으로 줄일 수 있습니다. 대가는 **유휴 CPU와 DB 읽기 부하**이고, 수신 프로세스마다 붙습니다. channels-nats(0.3ms, 유휴 비용 사실상 0)와 같은 지연을 얻으려면 프로세스마다 코어의 약 20%를 대기에 써야 합니다. 그러니 "자체 레이어를 보류한다"는 결론은 그대로이고, 근거만 "구조적 하한"에서 "**지연과 유휴 비용의 교환**, 그리고 레이어 의미론을 직접 책임지는 유지 비용"으로 바꿉니다.

### 2-2. "유휴 시 폴링은 읽기만 하므로 Litestream 복제 부담 없음" → 일반화는 틀림
- 측정 10초 동안 WAL 증가가 0이었던 것은 사실입니다.
- 하지만 코드상 빈 큐에서도 1% 확률로 `clean_expired()`가 돌고, 그 안에서 DELETE가 실행됩니다(`layers/__init__.py:250, 321`, `core.py:69-81`). 지울 행이 없으면 쓰기가 일어나지 않을 뿐, "읽기만 한다"는 아닙니다.
- 정정: "**만료 정리가 주기적으로 쓰기를 만든다.** 채널용 DB는 앱 DB와 분리하고 복제에서 뺀다."

### 2-3. "중복 0이므로 원자적 선점이 검증됨" → aio 판에는 코드 결함
- aio 레이어는 선점에 성공했는지를 `conn.total_changes > 0`으로 판정합니다(`aio.py:172`). `total_changes`는 **그 연결이 열린 뒤 누적된 변경 수**입니다. 그래서 이미 한 번이라도 쓴 연결이면 UPDATE에서 져도(0행) 참이 되고, **같은 메시지를 두 경쟁자가 모두 받을 수 있습니다.** Channels 규약의 "두 번 배달 금지"를 어깁니다.
- ORM 판은 `aupdate()`의 반환값(행 수)을 검사하므로 해당하지 않습니다(`core.py:47-50`).
- D2에서 중복 0이 나온 것은 aio 실행 때 경쟁 수신자 한쪽이 0건만 받았기 때문(`split=0/125`)으로 보입니다. 경쟁 재현은 [확인 필요]입니다.
- 외부 저장소이므로 우리가 이슈를 올리지는 않습니다(조직 규칙). 마스터께 보고만 합니다.

### 2-4. 표현 정정
- "아무도 없다", "첫 사례" → "**이번 조사 대상에는 없었다**"로 좁힙니다.
- channels-nats D2의 196/200은 `wait_for` 폴링 사이에 취소 공백이 생기는 문제(README에 명시된 의미론)의 영향일 수 있습니다. 하네스 문제로 분류하고 [확인 필요]로 둡니다.

## 3. 기각·보류한 리뷰 주장
- **"NATS를 범용 SQLite 패키지의 유일한 표준으로 올리는 것은 과하다"(리뷰어, channels-nats README:26 근거)**: 마스터가 방향을 정했으므로(nats 추천, redis 호환) 받아들이지 않습니다. 대신 리뷰 취지는 반영합니다.
  - 근거 문구(README:26)는 마르코가 조정합니다.
  - 의미론 차이(순서 보장, 수신 전 보관, `ChannelFull`, 취소 공백)는 **프로필 계약 문서로 명시**합니다. 추천이 과장되지 않도록 하기 위해서입니다.
  - 패키지는 레이어에 의존하지 않고, channels-nats는 `[nats]` extra로만 둡니다.
- "dj-lite 호환 API 불필요(표준 dict면 충분)": 받아들입니다. 자체 설정 생성기는 만들지 않고, 표준 `DATABASES`를 읽기만 합니다.

## 4. v0.1 범위 (수정안)
1. **boot CLI**(Django import 없음): guard 판정(`fresh/match/unknown`) → `unknown`이면 거부 → 복원 → 무결성 확인 → 배타 잠금 파일. 재시작해도 안전한 상태 전이로 설계합니다.
2. **`sqlite_doctor` 진단 명령**과 소수의 정적 체크
3. **헬스 뷰**: `caught_up/backlog/unknown` + 관측 시각
4. **배포 프로필 문서**: `single-server`(InMemory), `single-server-multiproc`(channels-nats 추천, channels_redis 호환), 레이어별 의미론 차이 표
5. **회귀 랩**: 2부 Docker 랩(SeaweedFS + toxiproxy)에 실패 경계 시나리오를 추가합니다. 메타만 유실, DB만 과거로 복원, 미복제 로컬 커밋, S3 조회 불가 중 부팅, 격리 중 종료, 복원 실패 후 재시작.
- **2단계 이후**: VFS 라우터(옵션), 테넌트 DB 보조, 자동 최신본 판정(이력 동일성 증명 방법이 정해진 뒤)
- **하지 않음**: 자체 채널 레이어, 설정 생성기, 백엔드 교체, writable VFS, NATS 서버 감독

## 5. 마스터 결정 목록 (갱신)

2. 이름: `django-sqlite-ops` / 기타
3. 공개 여부와 PO: 마르코(OSS) 관문으로 갈지, 당분간 내부 도구로 둘지
4. wireview 스타터 템플릿에 프로필 선택지를 넣을지(넣으면 wireview 변경 이슈가 따로 필요)
5. channels-lite aio 결함(`total_changes`)은 외부 저장소라 보고만 합니다. 마스터가 직접 알릴지 판단해 주세요.
