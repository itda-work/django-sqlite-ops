## 배포 프로필 종단 검증

### P1 — `single-server` (uvicorn 워커 1)

- **빈 이름 볼륨의 `/data` 소유자**: 처음 붙인 `appdata` 볼륨에서 `stat /data` → `10001:10001 755`. Docker 가 이미지 디렉터리의 소유자·권한까지 볼륨으로 복사한다.
- `python manage.py check --deploy`: `sqlite_ops.*` 0건.
- `BOOT_FLAGS=--init-new` 첫 부팅 → 응답까지 1.6초. 응답 PID 1개.
- `sqlite_doctor --litestream-config /etc/litestream.yml`: exit 0(channels `InMemoryChannelLayer` OK).
- 400건(요청당 1건) 쓰고 곧바로 `docker compose stop`(SIGTERM): **0.47초, exit 0, 복제본 400/400, integrity ok**(앞선 실행 0.39초·0.41초). 로그 순서:
  ```

  level=INFO msg="sending signal to exec process"
  ```

- 같은 볼륨으로 `BOOT_FLAGS` 를 비우고 재부팅: `state=match action=proceed reason_code=local_current` (local txid 4 ≥ remote txid 4), 400건.

## L1–L8

### L1 볼륨 없는 새 컨테이너 (무상태 교체)
볼륨 A 에 `--init-new` 로 200건을 쓰고 복제를 확인한 뒤 정상 종료. 볼륨 없는 컨테이너를 띄우자 `state=fresh action=restore reason_code=restore_from_remote` 로 복원하고 **1.6초 만에 200건으로 응답**했다(앞선 실행 2.2초). 이어 10건을 쓰고 종료하자 복제본 210건.

### L2 옛 볼륨 재부팅 (D4)
A 50건 → B 가 복원해 이어 써서 150건 → A 로 재부팅.
```
[boot] inputs: local_exists=True local_txid=2 remote=txid 4
[boot] decision: state=unknown action=refuse reason_code=remote_ahead reason=local txid 2 < remote txid 4
[boot] exit 2: refused (remote_ahead): local txid 2 < remote txid 4
```
복제본은 부팅 전후 모두 TXID 4·150건·integrity ok. A 의 DB 해시·50건 그대로. 보호가 없던 스파이크(docker D4)에서는 이 상황에서 150건이 55건으로 덮였다.

### L3 로컬 메타만 삭제
정상 종료 뒤 `/data/.app.sqlite3-litestream` 만 지우고 부팅 → exit 2 `no_local_meta`(remote txid 2). DB 해시·30건 그대로. 스파이크는 이 경우 원격으로 복원해 로컬을 버렸다(DESIGN §4-4).

### L4 S3 끊김 중 부팅
- toxiproxy 프록시를 끔(연결 거부): exit 2 `remote_error`, **30.5초**. 사유는 `litestream ltx timed out after 30s`. Litestream 0.5.17 의 `ltx` 는 연결 거부에도 곧바로 실패하지 않고 재시도하며 기다리므로, boot 의 `--ltx-timeout`(기본 30초)이 끊는다(재현함 — CLAUDE.md 함정에 추가).
- `timeout` toxic(연결은 받고 응답 없음) + `--ltx-timeout 5`: exit 2 `remote_error`, 5.5초.
- 두 경우 모두 DB 해시 그대로. 프록시를 되살린 뒤 같은 볼륨은 `match` 로 진행했다.

### L5 복제되지 않은 로컬 커밋
40건 복제 확인 → S3 끊음 → 25건 더 쓰고 3초 대기 → SIGKILL → S3 복구. 이때 복제본은 TXID 2·40건. 재부팅은 `state=match reason_code=local_current`(local txid 3 ≥ remote txid 2)로 진행해 **65건을 그대로 서비스**했고, 곧 복제본도 65건(TXID 3)이 됐다.

### L6 `--on-unknown restore` 도중 kill
L2 와 같은 옛 볼륨(remote_ahead)을 템플릿으로 두고, 매 kill 지점마다 새 볼륨에 복사해 `BOOT_FLAGS="--on-unknown restore"` 로 띄웠다. boot 의 rename 은 순식간이라 `lab_hooks/sitecustomize.py` 가 `os.rename` 뒤마다 5초 잠들게 하고(패키지 코드는 그대로), k 번째 rename 로그를 보면 `docker compose kill -s SIGKILL` 했다. kill 뒤 로그의 rename 줄 수가 정확히 k 인지 확인했다(sleep 에 기대지 않는다). 그다음 훅 없이 같은 옵션으로 다시 띄웠다.

검증(`lab/_checks.py` `quarantine_problems`, Docker 없는 단위 테스트 `tests/test_lab.py` 가 리뷰 1 의 합성 손상 상태 — 메타 비움, `-wal`·`-shm` 이 다른 격리 디렉터리 — 를 실패로 잡는 것을 확인): kill 전 템플릿의 격리 대상 **8항목**(DB, `-wal`, `-shm`, 메타 디렉터리와 그 하위 디렉터리 2개, L0 파일 2개)이 재실행 뒤 **같은 하나의** 격리 디렉터리에 같은 종류·SHA-256 으로 있고, 그 디렉터리에는 그것과 `manifest.json` 만 있으며, 템플릿 파일 내용이 그 밖 어디에도 없어야 한다. 설치 뒤 kill(D-14)이면 격리 디렉터리가 2개이고, 두 번째는 manifest 와 복원본 DB(+DB 사이드카)만 담고 메타가 없어야 한다.

| k | 직전에 끝난 rename | kill 시 rename 수 | kill 뒤 `.partial` | 재실행 판정 | 재실행 행 수 | 격리 디렉터리(실제/기대) | 검증 문제 |
|---|---|---|---|---|---|---|---|
| 1 | `manifest.json.tmp-* → manifest.json` | 1 | 1 | `fresh/restore`(재개 뒤) | 150 | 1/1 | 없음 |
| 2 | DB → `.partial/` | 2 | 1 | `fresh/restore` | 150 | 1/1 | 없음 |
| 3 | `-wal` → `.partial/` | 3 | 1 | `fresh/restore` | 150 | 1/1 | 없음 |
| 4 | `-shm` → `.partial/` | 4 | 1 | `fresh/restore` | 150 | 1/1 | 없음 |
| 5 | 메타 디렉터리 → `.partial/` | 5 | 1 | `fresh/restore` | 150 | 1/1 | 없음 |
| 6 | `.partial` → `stale-<ts>`(격리 완료) | 6 | 0 | `fresh/restore` | 150 | 1/1 | 없음 |
| 7 | 복원본 → DB 경로(설치) | 7 | 0 | `unknown/quarantine_and_restore`(`no_local_meta`, D-14) | 150 | 2/2 | 없음 |
| 8 | 상태 파일 | 8 | 0 | `unknown/quarantine_and_restore`(`no_local_meta`) | 150 | 2/2 | 없음 |

어느 지점에서도 재실행 뒤 `.partial` 이 남지 않았고, 템플릿의 DB·사이드카·메타가 갈라지거나 바뀌지 않았다. k=7·8 의 두 번째 격리 디렉터리는 설치된 복원본(메타 없음)이다 — DESIGN §4-3 이 말한 D-14 경로 그대로다.

### L7 복제본 손상 → 복원 실패
복제본의 LTX 객체 4개(L0·L1·L9)의 본문 가운데 64바이트를 SeaweedFS filer API 로 뒤집었다.
- 볼륨 없는 새 컨테이너: `fresh/restore` → `litestream restore exited with 1: ... decompress block: lz4: invalid source or destination buffer too short` → **exit 4**. 임시 복원 디렉터리를 조사용으로 남겼다.
- 메타를 지운 볼륨 + `--on-unknown restore`(`quarantine_and_restore`): 같은 오류로 **exit 4**. 복원이 격리보다 먼저라 **격리 디렉터리가 생기지 않았고 기존 파일 해시가 모두 그대로**였다. 남은 것은 `app.sqlite3.restore-<ts>-<rand>/` 하나.

### L8 헬스: S3 20초 끊김
`LAB_HEALTH_REFRESH=2`, `LAB_HEALTH_GRACE=10`(기본 15·60초면 20초 단절이 grace 안에 든다). 0.2초 간격으로 계속 쓰며 1초마다 헬스(상태·사유 코드·마지막 관측의 age)를 봤다.

- **L8a 업로드와 헬스 조회 모두 끊김**(같은 toxiproxy 프록시): 0–4.1초 `caught_up`(`db_changed_within_grace`, 끊기기 전 관측. age 1.0→5.1초), **5.1초(age 6.1초)부터 끝(19.2초, age 20.3초)까지 `unknown`(`stale`)**. 헬스의 `ltx` 조회가 30초 타임아웃까지 매달려 마지막 관측이 `REFRESH × 3`(6초)보다 오래됐기 때문이다(`remote_error` 는 20초 단절 안에 나오지 않았다). 복구 10.2초 뒤 `caught_up`. 쓰기 142건 오류 0, 종료 뒤 복제본 162건 = 로컬.
  - 판정 기준(`_checks.full_outage_problems`, 리뷰 1 반영): 표본 순번이 아니라 경과 시간과 age 로 본다. 전환 제한은 `REFRESH × 3` + 진행 중 조회 여유 `REFRESH` + 표본 간격 1초 + 여유 1초 = **10초**다. 이 10초는 **랩이 정한 허용 시간(가정)**이지 보장된 상한이 아니다: `health.py` 는 조회 하나가 끝나는 시간을 제한하지 않고 관측 시각을 조회가 끝날 때 찍으므로, 단절 직전에 시작한 조회가 `REFRESH` 보다 오래 걸려 성공하면 전환이 더 늦을 수 있다(그때 L8a 는 실패로 알린다). age 비교는 응답 age 의 반올림(소수 셋째 자리)만큼 허용한다(리뷰 2: 관측 6.0004초 뒤 응답은 `stale` 이지만 age 는 6.0). 단절 직전에 관측이 갱신됐으면 5.1초에 `caught_up` 이어도 정상이고(실제 `health.alias_status` 로 만든 타임라인으로 단위 테스트), 전환 뒤에는 단절이 끝날 때까지 `unknown` 이 유지돼야 한다. 이번 실행은 5.1초 전환·유지로 통과.
- **L8b 업로드 경로만 끊김**(헬스는 다른 프록시 `s3h` 로 조회): 1–11초 `caught_up`(`local_ahead_within_grace`), **12.1초부터 `backlog`(`local_ahead`)**. 복구 14.2초 뒤 `caught_up`. 쓰기 161건 오류 0, 복제본 181건 = 로컬.
- 판정: DESIGN §10 의 기대 "`backlog` → `caught_up`" 은 조회가 되는 경우(L8b)에만 맞다. S3 전체가 끊기면 §7 표대로 `unknown` 이 먼저다. 두 상태 모두 `caught_up` 이 아니므로 "본문 `status` 가 `caught_up` 이 아니면 경보"라는 운영 규칙으로는 둘 다 잡힌다. 쓰기 쪽은 docker D2 처럼 단절 중에도 오류가 없었다.

## 새로 재현한 함정

- Litestream 0.5.17 `ltx` 는 S3 연결 거부에도 곧바로 실패하지 않는다(L4: 30.5초). boot 는 `--ltx-timeout` 덕에 거부로 끝나고, 헬스는 그동안 `stale` 이 된다(L8a).
- Docker Compose 5.5.1 은 어느 서비스도 쓰지 않거나 비활성 프로필 서비스만 쓰는 볼륨을 모델에서 빼서 `down -v` 가 지우지 않는다(`config --volumes` 에 없음). 랩은 모든 풀 볼륨을 붙인 시작하지 않는 서비스를 두고 `--profile app down -v` 로 지운다.
