# 최신 로컬 L0 손상 뒤 복원본의 행 (#124, 2026-11-19)

#115 는 최신 로컬 L0 가 깨진 뒤의 **헬스 판정**만 봤다. 0.5.18 은 그 뒤에도 sync 가 이어지고 컴팩션만 멈춘다([#115 기록](lab-2026-11-13-health-pipeline-stall.md)). 그때 만든 복원본에 원격에 반영된 커밋이 모두 있는지, 깨뜨린 L0 의 커밋이 온전히 돌아오는지는 미검증이었다(DESIGN §12). 이 기록은 그 질문에 답한다. 데이터 유실 보고에서 시작한 것은 아니다.

환경: macOS 26.6.2 arm64. Litestream 0.5.17(Homebrew `/opt/homebrew/bin/litestream`, SHA-256 `205b4c31…88bb73`)과 0.5.18(릴리스 `litestream-0.5.18-darwin-arm64.tar.gz` 의 바이너리, SHA-256 `37b5332f…9395b3`). 파일 복제본을 썼다. Python 3.14.7, SQLite 3.53.1(uv).

## 방법

`tests/test_health_pipeline.py` 의 `test_real_corrupt_latest_l0` 를 늘렸다. 손상 창을 찾는 부분은 #115 와 같다. L1 주기는 4초다.

1. 연결 하나를 쥔 쓰기 스레드가 0.2초마다 500바이트 행을 쓴다. 로컬 L0 가 TXID 3 에 닿을 때까지 기다린다(아래 'TXID ≥ 3').
2. 쓰기를 멈추고(`Writer.pause()` 는 진행 중인 쓰기가 끝날 때까지 기다린다) 헬스가 `in_sync` 가 될 때까지 기다린다. `in_sync` 는 `-wal` 의 모든 커밋이 최신 L0 안에 있고 원격 TXID ≥ 로컬 TXID 라는 뜻이다. 그 시점의 행 수를 `pre_rows` 로 두고, 아직 컴팩션되지 않은 최신 L0 를 깨뜨린다(헤더 뒤 64바이트 반전).
3. 쓰기를 재개한다. 헬스가 판별 표의 `backlog` 사유를 낼 때까지 기다린다. 손상 뒤 10행 이상을 더 쓰고 멈춘다(`all_rows`).
4. 원격 반영의 근거는 시간 경과가 아니라 다음 확정 근거로 정한다.
   - 0.5.18: WAL 근거가 `IN_SYNC` 이고 `remote_max_txid == local_max_txid` 가 될 때까지 폴링한다(30초 제한).
   - 0.5.17: WAL 근거가 `PENDING` 이고 로컬·원격 최대 TXID 가 깨뜨린 L0 의 TXID 그대로다.
5. Litestream 을 멈춘다. 원격 최대 TXID `N` 을 다시 보고(관측값 이상) 별도 경로로 `restore -o` 한다(`boot.litestream.restore`, `integrity_check="none"`). 복원 TXID ≥ `N` 이어야 한다.
6. 복원본의 `PRAGMA integrity_check` 가 `ok` 이고 id 가 1..기대 행으로 구멍이 없어야 한다. `(id, v)` 전체가 라이브 DB 의 앞 기대 행과 같아야 한다. 기대 행은 판별 표 `LATEST_L0_CORRUPTION["restored_rows"]` 다. 0.5.18 은 `all`(`all_rows`), 0.5.17 은 `pre_corruption`(`pre_rows`)이다.

## 결과 (재현함)

| 판 | 통과 | 깨뜨린 L0 | `N` = 복원 TXID | 복원 행 / 라이브 행 |
|---|---|---|---|---|
| 0.5.17 | 11/11 | 0x4 또는 0x9 | 깨뜨린 L0 와 같다 | `pre_rows`(16·37·38) / 37~64 |
| 0.5.18 | 11/11 | 0x4 또는 0x6 | 0xb~0xe | `all_rows`(47~54) / 같음 |

- **0.5.18**: 손상 뒤 커밋까지 모든 행이 복원되고 값이 같다. 깨뜨린 L0 의 커밋은 원격 사본(손상 전에 올라간 것)으로 돌아온다. 그 뒤의 L0 들도 깨진 로컬 파일 없이 복원된다. 손상 뒤에도 sync 가 이어지는 것(#115)이 복원본에도 맞다.
- **0.5.17**: sync 가 깨뜨린 L0 에서 멈춘다. 복원본은 손상 전 행만 담고 값이 같다. 손상 뒤 행은 원격에 없다. 헬스는 이를 `backlog/db_not_replicated` 로 알린다(#115).
- 한 번 도는 데 9~31초 걸린다. 손상 창을 바로 찾으면 약 10초, 쓰기를 재개해 다시 찾으면 약 30초다.
- TXID ≥ 3 조건을 넣기 전의 첫 실행(각 판 1회)은 0.5.17 이 TXID 1, 0.5.18 이 TXID 2 를 깨뜨렸다. 그때도 같은 결과로 통과했다.

## 음성 대조 (재현함)

저장소 밖 임시 worktree 에 이 변경을 적용하고 테스트를 하나씩 바꿔 실패하는지 봤다. 각 변이는 한 번씩 돌렸다.

| 변이 | 결과 |
|---|---|
| 판별 표의 `restored_rows` 를 두 판 사이에서 맞바꿈 | 0.5.17 은 `IN_SYNC` 대기 시간 초과(WAL `pending`), 0.5.18 은 로컬 TXID 11 ≠ 깨뜨린 L0 4 로 실패 |
| 복원 전에 **원격**의 깨뜨린 L0 사본도 깨뜨림 | 두 판 모두 `restore` rc 1(`decode database: … lz4: invalid source`) — 복원이 실제로 그 원격 사본을 읽는다 |
| 복원본의 id 1 값을 바꿈(0.5.18) | `(id, v)` 비교가 index 0 에서 실패 — 값까지 비교한다 |

## TXID ≥ 3

깨뜨리는 최신 L0 가 첫 L0(TXID 1, DB 전체)도 아니고 그 바로 뒤 첫 증분도 아니게 하려는 조건이다. 그러면 복원은 온전한 증분을 하나 이상 적용한 뒤 깨뜨린 증분을 원격 사본으로 읽는다. '증분'만 바란다면 2 로 충분하다. 3 이 필요하다는 실측은 없다. 게이트 전 실행(TXID 1·2)도 통과했다. 흔한 경우를 고정하려는 선택이다.

## 한계 (미검증)

- 로컬 L0 가 **업로드 전에** 깨지는 경우. 원격까지 손상이 전파된다(#106 한계). 별도 이슈 대상이다.
- 원격 L0·L1 이상의 손상(랩 L7 은 원격 손상 → 복원 실패만 본다), L0 가 수 시간 쌓인 뒤의 복원 시간.
- 실제 S3·R2, amd64, Linux.
- 컴팩션이 계속 멈춘 채 보존 정리·스냅샷이 도는 긴 운용(이번에는 수십 초).
