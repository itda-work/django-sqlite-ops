# `cache_size` 단독 악화의 원인 (#27, 2026-10-12)

#10 벤치에서 `cache_size=-65536` 단독만 5회 모두 나빠졌고(처리량 −8~−12%, p99 +17~+27%, `CONN_MAX_AGE=0`), 네 후보를 함께 켜면 재현되지 않았다([`lab-2026-10-08.md`](lab-2026-10-08.md#pragma-벤치)). #26 재측정에서는 같은 조건이 −9.9, −9.8, −4.6, −15.0, **+19.0**% 로 '재현 안 됨'이었다([`bench-2026-10-08.md`](bench-2026-10-08.md)). 이 문서는 질문을 둘로 나눠 답한다.

1. **효과가 실재하는가.** 랩 소음이 없는 최소 재현에서, 연결마다 열고 닫는 패턴(`CONN_MAX_AGE=0`)에 `cache_size=-65536` 이 비용을 더하는가.
2. 실재한다면 **무엇 때문인가.** 그리고 그 원인이 랩 결과(#10 의 악화, 네 개를 함께 켜면 사라짐, #26 의 흔들림)를 설명하는가.

근거는 **재현함**(이 측정에서 다시 일어남), **코드상 확인**(SQLite 3.46.1 소스를 읽음), **추정**(수치에서 미루어 봄), **미검증**으로 나눠 적는다.

## 요약

- **실재한다(재현함).** 표준 라이브러리 `sqlite3` 만 쓴 최소 재현에서 `cache_size=-65536` 단독은 macOS(SQLite 3.53.1)와 Linux 컨테이너(랩 이미지, SQLite 3.46.1) 모두 `perconn`(요청마다 열고 닫기)의 **모든 조건**(DB 크기 2 × 스레드 2)에서 '재현(나빠짐)'이었다. 처리량은 −15~−82%, p99 는 +26~+370% 였다(블록 12, 사전에 정한 신뢰구간 판정). `mmap_size` 와 함께 켜거나 네 후보를 다 켜면 악화가 사라지고 오히려 좋아졌다. #10 과 같은 모양이다.
- **원인(재현함 + 코드상 확인)**: 요청 하나가 기본 캐시(2,000 KiB ≈ 500 페이지)보다 많은 페이지를 읽을 때 생긴다. SQLite 페이지 캐시는 상한(`nMax`)에 닿아야 페이지 버퍼를 재활용하고, 그 전에는 페이지마다 새로 할당한다(pcache1.c). 기본 캐시에서는 랩의 정렬 요청(약 2,000 페이지)이 500 페이지 안에서 버퍼를 돌려 쓴다. 캐시를 키우면 2,000 페이지를 모두 새로 할당하고, 연결을 닫을 때 모두 해제한다. Linux 에서 정렬 1건당 pcache 할당 최고치가 3.2 → 8.8 MiB, 할당 수가 1,058 → 2,418, minor page fault 가 490 → 1,836 으로 늘었다. 그 결과 정렬은 −33%(1스레드)·−68%(16스레드)로 느려졌고, pk 읽기(몇 페이지)는 1스레드에서 5% 미만이었다. 크기가 아니라 **상한을 넘느냐**가 갈림길이다: `-8192`(8 MiB)도 64 MiB 와 똑같이 나빠졌다.
- **`mmap_size` 와 함께면 사라지는 이유(재현함 + 코드상 확인)**: mmap 으로 읽는 페이지는 pcache 버퍼를 쓰지 않는다(pager.c `pagerAcquireMapPage`). 같은 정렬의 pcache 할당이 1.2 MiB 로 줄고 `cache_size` 와 무관해졌다.
- **연결을 재사용해도 다른 연결이 쓰면 같다(재현함 + 코드상 확인)**: WAL 에서 읽기 트랜잭션을 시작할 때 다른 연결의 쓰기로 WAL 이 바뀌었으면 캐시 전체를 비운다(pager.c `pager_reset`). 16 스레드 `reuse` 에서 쓰기 없는 정렬은 `cache_size` 로 좋아졌지만(+661%/+36%), 쓰기 20% 를 섞으면 나빠졌다(−47%/−62%).
- **랩 결과를 설명한다(재현함, 원자료 재분석)**: #10 원자료에서 정렬/읽기 평균 지연 비는 `cache_size` 단독이 5회 모두 1.43–1.46(같은 반복의 기준 1.25–1.28), `mmap_size`·'넷 다'는 1.14–1.16 이었다. #26 에서 처리량이 +19.0% 로 나온 반복 5 도 정렬/읽기 비가 1.595(기준 1.302)로, 정렬 쪽 비용은 5회 모두 있었다. #26 의 '재현 안 됨'은 실행 사이 흔들림(기준 처리량 표준편차 약 7%)이 처리량 짝 차이를 덮었기 때문이다. 같은 실행 안의 비율로 보면 사라지지 않았다. 새 랩 실행은 하지 않았다(아래 '랩 확인').
- **미리 할당하지 않는다(코드상 확인 + 재현함)**: `cache_size` 를 올려도 연결을 열 때 64 MiB 를 잡지 않는다. 첫 일괄 할당은 `SQLITE_DEFAULT_PCACHE_INITSZ`(20 페이지)와 `nMax` 중 작은 쪽이다. PRAGMA 단계 p50 은 +1.5µs 안팎이었고, pk 읽기 연결의 SQLite 메모리 최고치는 기준과 같았다(1.5 MiB).
- **제안(기본값은 바꾸지 않는다)**: `cache_size` 는 '켜지 않음'을 유지하고, 근거를 #10 의 처리량 수치에서 이 기전으로 바꾼다. 안내: **`CONN_MAX_AGE=0`(연결마다 새로 열기)이거나 여러 연결이 쓰는 환경에서는 `cache_size` 를 기본보다 올리지 말 것.** 캐시는 연결마다 비어 시작하거나 쓰기 때마다 비워지므로 크게 해도 다시 쓰이지 않는다. 기본 상한보다 많은 페이지를 읽는 요청에서는 할당·해제 비용만 늘어난다. `mmap_size` 는 이 측정에서 정렬을 빠르게 했지만 pk 읽기 연결은 −16~−20% 느리게 했고(연결마다 매핑, 요청당 minor fault 약 3) 랩 #10 에서도 재현된 개선이 없어 기본값 후보로 올리지 않는다.

## 방법

`lab/cache_probe.py`(본 측정)와 `lab/cache_mech.py`(원인 가설). 둘 다 표준 라이브러리만 쓴다. 집계·판정은 `lab/_cachestat.py`(순수 함수, `tests/test_lab.py` 가 Docker 없이 검사), 아래 표는 `lab/cache_report.py` 가 원자료에서 만든 출력 그대로다.

- **스키마·쿼리**: 랩 `notes` 앱과 같다. 테이블 `notes_note(id, body, score, created)` + `score` 인덱스, 씨앗 `Random(10)`·본문 200자(`lab_seed` 와 같음). 요청 하나는 읽기 70%(pk 로 1행, Django `.first()` 의 SQL), 정렬 10%(`score` 구간 20,000 → 약 2,000행을 `body`·`created` 로 정렬해 20행, 랩 `/lab/sorted`), 1행 쓰기 20%(`BEGIN IMMEDIATE` … `INSERT … RETURNING`, Django `bulk_create`).
- **연결**: `perconn` 은 요청마다 open → PRAGMA → 요청 → close 이고 각 단계 시간을 잰다. PRAGMA 는 Django 6.1 sqlite3 백엔드가 거는 두 줄(`foreign_keys = ON`, `legacy_alter_table = OFF`) + 이 패키지 권장 PRAGMA(`database.py` 의 표, 테스트가 같은지 검사) + 변형이다. `reuse` 는 스레드마다 연결 하나를 칸 내내 쓴다(대조). Django 가 연결마다 등록하는 Python 함수 등록은 하지 않았다(변형과 무관하게 같은 비용).
- **holder 연결**: 조건 내내 연결 하나를 열어 둔다(랩의 Litestream 대역, 트랜잭션은 잡지 않음). 첫 본 측정 시작 직후에 단일 스레드 `perconn` 의 close 가 매번 '마지막 연결 닫기'가 되어 체크포인트·`-wal` 삭제가 끼어드는 것을 보고(close p50 약 120µs → holder 를 넣으면 약 11µs) 하네스를 고쳤다. 그 실행은 멈추고 두 환경 모두 처음부터 다시 돌렸다(멈춘 실행 `prelim-noholder-*.jsonl` 은 판정에 쓰지 않음).
- **조건**: DB 크기 `small`(행 100,000, 25.7 MiB, 랩과 같은 규모)·`large`(행 400,000, 102.9 MiB, 64 MiB 캐시보다 큼) × 스레드 1·16 × 연결 패턴 `perconn`·`reuse`. 조건마다 템플릿 DB 를 새 하위 디렉터리로 복사한다.
- **변형**: 기준(권장 PRAGMA 만), `cache_size=-65536`, `mmap_size=268435456`, 둘 다(`cache_mmap`), 네 후보 다(`all4`: `temp_store=MEMORY`·`mmap_size`·`cache_size`·`journal_size_limit=67108864`). 값은 랩 벤치와 같다.
- **순서 효과**: 조건마다 버리는 워밍업 칸 하나, 그 뒤 블록 12개. 블록마다 변형 순서를 무작위로 섞고(시드 = 블록 번호, 두 환경이 같은 순서) 칸 하나를 1.5초 닫힌 루프로 돈다. 짝 차이는 같은 블록의 기준과 낸다.
- **계측**: 처리량, 요청 지연 p50·p99(최근접 순위), `perconn` 단계별 시간, 칸 끝 RSS, Linux 에서는 `sqlite3_status64(SQLITE_STATUS_MEMORY_USED)` 최고치(칸마다 초기화). macOS 의 uv Python 은 SQLite 를 정적으로 넣어 ctypes 로 같은 인스턴스에 닿지 않는다(`CDLL(None)` 은 시스템 사본 3.51.0 을 잡는다, 확인함) — RSS 만 남겼다.

### 사전에 정한 판정 기준

본 측정 전에 `.work/issue-27/criteria.md` 에 적고 `_cachestat.py` 로 구현했다.

- 1차 지표 처리량, 2차 p99. 블록 짝 차이 (변형 − 기준)/기준 × 100 의 평균과 t 분포 95% 신뢰구간.
- 구간이 0 을 포함하지 않고 |평균| ≥ 5% → **재현(나빠짐/좋아짐)**. 구간이 (−5%, +5%) 안 → **5% 이상 효과 없음**. 그 밖 → **판정 불가**.
- 보조: #26 규칙(모든 블록에서 같은 방향으로 5% 이상).
- 질문 1 의 답은 macOS·Linux 의 `perconn` 에서 `cache_size` 의 1차 판정이다. 두 환경에서 같은 방향으로 '재현'일 때만 "효과가 실재한다"고 쓴다.
- 다중 비교(조건 16 × 변형 4 = 64 검정)를 감안해 5% 크기를 함께 요구하고, 한 조건만 튄 것은 근거로 쓰지 않는다.

원인 가설 측정(`cache_mech.py`)의 예측도 측정 전에 같은 파일에 적었다(판정 기준 같음, 블록 6, 칸 1초).

- **H1**(연결당 많이 읽는 요청): `perconn` 읽기 전용은 `cache_size` 효과 5% 미만, 정렬 전용은 나빠진다. PAGECACHE_OVERFLOW 최고치가 64 MiB 에서 기본보다 크다. `mmap_size` 를 함께 켜면 사라진다. `-8192` 는 그 사이.
- **H2**(재사용 연결의 WAL 변경 무효화): `reuse` 16 스레드에서 쓰기 없는 정렬은 `cache_size` 가 나빠지지 않고, 쓰기 20% 를 섞으면 나빠진다.

### 문서·설정에 주는 것

- `database.py` 기본값은 바꾸지 않는다. `cache_size` 는 계속 '켜지 않음'이다.
- 안내를 근거와 함께 넣는다: `CONN_MAX_AGE=0` 이거나 여러 연결이 쓰는 환경에서는 `cache_size` 를 기본보다 올리지 말 것. 캐시가 연결마다 비어 시작하거나 쓰기 때마다 비워지므로 다시 쓰이지 않고, 기본 상한보다 많은 페이지를 읽는 요청에서 할당·해제만 늘어난다. 큰 캐시가 이득인 경우는 한 연결을 오래 쓰고 다른 연결의 쓰기가 드문 경우다(H2 의 쓰기 없는 `reuse`).
- 제안(적용 안 함): `sqlite_doctor` 나 시스템 체크가 `CONN_MAX_AGE=0` 과 `cache_size` 상향을 함께 보면 알리는 것. 경고 기준(어느 크기부터인지)의 근거가 없어 이 이슈에서는 만들지 않는다.

## 미검증

- 전역 mutex 경합이 16 스레드 악화에 얼마나 기여하는지(perf·lock 통계로 재지 않았다).
- 16 스레드 pk 읽기에서 `cache_size` 의 −9%.
- 랩에서 정렬 비율만 바꾼 확인(위 '새 랩 실행을 하지 않은 것').
- amd64, 다른 libc(musl)·할당기, SQLite 3.37.2(`sqlite-floor`) 같은 다른 판. 3.46.1 과 3.53.1 두 판에서만 재현했다.
- 64 MiB 를 넘는 DB 에서 `mmap_size` 가 mmap 한도(256 MiB)를 넘는 경우, WAL 이 큰 경우(WAL 의 프레임은 mmap 으로 읽지 않는다 — `getPageMMap` 은 WAL 에 없는 페이지만, 코드상 확인)에 `cache_mmap` 이 여전히 악화를 없애는지.
- Django 가 연결마다 등록하는 Python 함수(수십 개)의 비용은 넣지 않았다. 변형과 무관하게 같다고 보지만 확인하지 않았다.
