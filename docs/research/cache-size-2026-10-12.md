# `cache_size` 단독 악화의 원인 (#27, 2026-10-12)

#10 벤치에서 `cache_size=-65536` 단독만 5회 모두 나빠졌다(처리량 −8~−12%, p99 +17~+27%, `CONN_MAX_AGE=0`). 네 후보를 함께 켜면 재현되지 않았다([`lab-2026-10-08.md`](lab-2026-10-08.md#pragma-벤치)). #26 재측정에서는 같은 조건이 −9.9, −9.8, −4.6, −15.0, **+19.0**% 로 '재현 안 됨'이었다([`bench-2026-10-08.md`](bench-2026-10-08.md)). 이 문서는 질문을 둘로 나눠 답한다.

1. **효과가 실재하는가.** 랩 소음이 없는 최소 재현에서, 연결마다 열고 닫는 패턴(`CONN_MAX_AGE=0`)에 `cache_size=-65536` 이 비용을 더하는가.
2. 실재한다면 **무엇 때문인가.** 그리고 그 원인이 랩 결과를 설명하는가.

근거는 **재현함**(이 측정에서 다시 일어남), **코드상 확인**(SQLite 3.46.1 소스를 읽음), **추정**(수치에서 미루어 봄), **미검증**으로 나눠 적는다. '확인'은 측정 전에 고정한 예측이 두 환경에서 모두 맞은 경우만 쓴다.

## 진행 순서: 첫 실행은 탐색적, 재실행으로 확인

1. **첫 실행(탐색적, 14:39–15:18 KST).** 본 측정(`cache_probe.py`)과 원인 가설 측정(`cache_mech.py`)을 한 번씩 돌렸다. 리뷰 1 에서 세 가지가 드러났다.
   - **기록 시각**: 판정 기준 파일(`.work/issue-27/criteria.md`)에 적은 "14:45"(holder 절)와 "15:25"(가설 절)는 시계를 읽은 값이 아니라 잘못 적은 시각이었다. 당시 기록을 대조했다(정정만 덧붙이고 원래 시각은 고치지 않았다).
     - 파일 생성(birth) 14:39:02 → 첫 측정(멈춘 `prelim-noholder`) 시작 14:39:04. 판정 기준 절은 첫 측정 전에 있었다.
     - holder 절: 같은 명령에서 고친 실행 스크립트의 mtime 14:42:38, 채택한 macOS 본 측정 시작 14:42:40. 파일 mtime 은 뒤 수정으로 덮였으므로 이 절이 측정 전에 있었다는 것은 파일 기록만으로 입증할 수 없다.
     - 가설 절: 파일 마지막 수정 15:09:43(= `cache_mech.py` 생성 시각), 가설 측정 시작 15:10:47. 측정 전에 적었지만 **본 측정 결과를 본 뒤에 세운 가설**이다.
     - 그래서 첫 실행의 결과는 모두 **탐색적**으로 다룬다.
   - **워커 실패 미검출**: 두 스크립트 모두 워커 스레드가 예외로 죽어도 칸이 정상값(오류 0)으로 집계됐다(리뷰가 오류 주입으로 재현함). 첫 실행 원자료의 "오류 0건"은 워커 실패가 없었다는 증거가 되지 못한다(그 실행에 실제 실패가 있었는지는 **미검증**).
   - **반례**: 첫 실행은 연결 하나에 쿼리 하나만 냈다. 리뷰는 요청마다 새 연결에서 같은 정렬을 10번 내면 64 MiB 캐시가 처리량을 +81~+122% 올리는 것을 재현했다(macOS). 첫 문서의 "연결마다 비어 시작하므로 다시 쓰이지 않는다"는 측정 범위를 넘었다.
2. **하네스 수정.** 워커 예외는 barrier 를 깨고 칸을 실패로 올려 실행을 멈춘다(SQLite 오류는 세고 계속한다). 수정 전에 실패하는 오류 주입 테스트 6개로 증명했다(`tests/test_lab.py`). 본 측정에 `perconn10`(연결 하나에서 요청 10개), 가설 측정에 `sort10same`·`sort10diff`(연결 하나에서 정렬 10회, 같은 구간·다른 구간)를 넣었다.
3. **재실행(확인, 16:17:56–17:08:41 KST).** 16:17:43 에 예측을 고정했다(`criteria.md` 의 '재실행 기준' 절, sha256 `7d6d5833e868…`, 재실행 로그 첫 줄에 같은 해시). 두 측정을 처음부터 다시 돌렸고 첫 실행과 섞지 않았다. 재실행은 네 실행 모두 exit 0 이고, 수정한 하네스에서는 워커 예외가 나면 실행이 멈추므로 **재실행에는 워커 실패가 없었다**(재현함). 이 문서의 수치는 재실행 것이다. 첫 실행 표는 부록에 둔다.

## 요약 (재실행)

- **실재한다(확인).** 연결 하나에서 요청 1개(`perconn`) 또는 혼합 요청 10개(`perconn10`)를 처리하고 닫을 때, `cache_size=-65536` 단독은 macOS(SQLite 3.53.1)·Linux 랩 이미지(3.46.1)의 여덟 조건(크기 2 × 스레드 2 × 패턴 2) 모두에서 '재현(나빠짐)'이었다. `perconn` 처리량 −15~−80%, p99 +24~+374%, `perconn10` 처리량 −20~−79%.
- **원인(확인 + 코드상 확인)**: 요청이 기본 캐시 상한(2,000 KiB ≈ 500 페이지)보다 많은 페이지를 읽는데 그 페이지를 같은 연결에서 다시 읽지 않을 때 생긴다. SQLite 페이지 캐시는 상한에 닿아야 버퍼를 재활용하고 그 전에는 페이지마다 새로 할당한다(pcache1.c). 정렬 하나(약 2,000행)를 읽고 닫는 연결은 기본 캐시에서 버퍼를 돌려 쓰지만, 캐시를 키우면 읽는 페이지마다 새로 할당하고 닫을 때 모두 해제한다. Linux 1스레드 정렬 1건: pcache 할당 최고 3.2 → 8.8 MiB, 동시 생존 할당 수 최고 1,058 → 2,418, 요청당 minor fault 490 → 1,841, 처리량 −35%. pk 읽기는 1스레드에서 5% 미만. 8 MiB 도 64 MiB 와 같이 나빠진다.
- **같은 연결에서 같은 페이지를 다시 읽으면 반대로 좋아진다(확인, 리뷰 1 반례).** 새 연결에서 같은 구간 정렬을 10번 내면 `cache_size` 는 +50~+326%(두 환경, 1·16 스레드)였다. 매번 다른 구간이면 환경에 따라 갈렸다(macOS +9/+40%, Linux 판정 불가/−55%, 탐색적).
- **여러 연결이 쓰면 재사용 연결도 나빠진다(확인 + 코드상 확인).** WAL 에서 읽기 트랜잭션을 시작할 때 다른 연결의 쓰기로 WAL 이 바뀌었으면 캐시 전체를 비운다(pager.c). 16 스레드 `reuse` 에서 쓰기 없는 정렬은 `cache_size` 로 +47~+496% 좋아졌지만, 쓰기 20% 를 섞으면 −45~−62% 나빠졌다. 본 측정 `reuse` 16 스레드(쓰기 20%)도 −44~−73%.
- **`mmap_size` 와 함께면**: 정렬처럼 많은 페이지를 읽는 요청에서 `cache_size` 의 추가 비용은 사라졌다 — 가설 측정에서 `cache_mmap` 은 모든 정렬 조건에서 `mmap_size` 단독과 같은 수준이고 pcache 할당이 1.2 MiB 로 `cache_size` 와 무관하다(재현함, mmap 페이지는 pcache 버퍼를 쓰지 않음 — 코드상 확인). 다만 본 측정에서 "`cache_mmap`·`all4` 는 나빠지지 않는다"는 예측(C2)은 8칸 중 6칸만 맞았다. macOS `small` 16 스레드 `perconn` 에서 `cache_mmap` −41%·`all4` −57%, Linux `large` 1 스레드 `perconn` 에서 `all4` −9% 였다. 두 칸 모두 `mmap_size` 단독도 음수(−32%, −6%)였다(첫 실행 문서는 이 macOS 칸을 놓치고 "함께 켜면 사라진다"고 일반화했다).
- **미리 할당하지 않는다(코드상 확인 + 재현함)**: 첫 일괄 할당은 20 페이지와 상한 중 작은 쪽이다. 1 스레드에서 PRAGMA 단계 p50 은 +1~2µs, pk 읽기 연결의 SQLite 메모리 최고치·할당 수는 세 캐시 크기에서 같다.
- **랩 원자료(관측)**: #10 에서 정렬/읽기 평균 지연 비가 `cache_size` 단독 5회 모두 1.43–1.46(같은 반복의 기준 1.25–1.28)이었다. #26 도 5회 모두 1.540–1.624(기준 1.302–1.383)이다. 최소 재현의 기전과 일관된다. #26 의 '재현 안 됨'이 실행 간 흔들림에 가려진 것이라는 해석은 **추정**이다(아래 결과 3).
- **권고(측정 범위 안에서, 기본값은 바꾸지 않음)**: `cache_size` 는 '켜지 않음'을 유지한다. 측정한 조건 중 **연결당 요청 1~10개의 혼합 부하(인덱스 없는 정렬 10%)**, **연결 하나에서 많은 페이지를 한 번씩만 읽는 요청**, **여러 연결이 쓰는 재사용 연결**에서는 `cache_size` 상향이 처리량을 크게 떨어뜨렸다. 반대로 **한 연결(요청·트랜잭션) 안에서 같은 페이지를 다시 읽는 요청**과 **다른 연결의 쓰기가 없는 재사용 연결**에서는 좋아졌다. 어느 쪽인지는 부하에 달렸으므로 올리려면 자기 부하로 잰다.

## 사전에 정한 예측과 판정 (재실행)

`criteria.md` '재실행 기준' 절(16:17:43 고정). 판정 규칙은 첫 실행과 같다: 블록 짝 차이 (변형 − 기준)/기준 × 100 의 평균과 t 분포 95% 신뢰구간이 0 을 벗어나고 |평균| ≥ 5% 면 **재현**, 구간이 (−5%, +5%) 안이면 **5% 이상 효과 없음**, 그 밖은 **판정 불가**(`_cachestat.verdict`). 보조로 #26 규칙(모든 블록 같은 방향 5% 이상). 처리량 기준. 두 환경에서 모두 맞아야 '확인'이다.

| 예측 | macOS | Linux | 판정 |

## 방법

`lab/cache_probe.py`(본 측정)와 `lab/cache_mech.py`(원인 가설). 표준 라이브러리만 쓴다. 집계·판정은 `lab/_cachestat.py`(순수 함수, `tests/test_lab.py` 가 Docker 없이 검사), 아래 표는 모두 `lab/cache_report.py` 가 원자료에서 만든 출력 그대로다.

- **스키마·쿼리**: 랩 `notes` 앱과 같다. 테이블 `notes_note(id, body, score, created)` + `score` 인덱스, 씨앗 `Random(10)`·본문 200자. 요청 하나는 읽기 70%(pk 로 1행, Django `.first()` 의 SQL), 정렬 10%(`score` 구간 20,000 → 약 2,000행을 `body`·`created` 로 정렬해 20행, 랩 `/lab/sorted`), 1행 쓰기 20%(`BEGIN IMMEDIATE` … `INSERT … RETURNING`).
- **연결 패턴(본 측정)**: `perconn` 은 연결 하나에 요청 1개(open → PRAGMA → 요청 → close), `perconn10` 은 연결 하나에 같은 혼합의 요청 10개(Django 요청 하나가 쿼리 여러 개를 내는 경우, 리뷰 1), `reuse` 는 스레드마다 연결 하나를 칸 내내 쓴다. 처리량은 요청(쿼리) 수로 세고, 지연은 `perconn`·`perconn10` 에서 연결 한 바퀴다. PRAGMA 는 Django 6.1 sqlite3 백엔드의 두 줄(`foreign_keys = ON`, `legacy_alter_table = OFF`) + 이 패키지 권장 PRAGMA(`database.py` 의 표, 테스트가 같은지 검사) + 변형이다. Django 가 연결마다 등록하는 Python 함수는 넣지 않았다.
- **요청 종류(가설 측정)**: `read`(pk 1행), `sort`(정렬 1회), `sort10same`(연결 하나에서 같은 구간 정렬 10회), `sort10diff`(연결 하나에서 다른 구간 정렬 10회), `sortwrite`(정렬 80%·쓰기 20%, `reuse` 만). 설정은 `cache_size` 기본·`-8192`(`cache8m`)·`-65536` × `mmap_size` 0·256 MiB.
- **holder 연결**: 조건 내내 연결 하나를 열어 둔다(랩의 Litestream 대역, 트랜잭션은 잡지 않음). 없으면 단일 스레드에서 close 가 매번 마지막 연결 닫기가 되어 체크포인트·`-wal` 삭제가 끼어든다(첫 실행 중 발견, close p50 약 120µs → 11µs).
- **크기**: 본 측정 `small`(행 100,000, 25.7 MiB)·`large`(400,000, 102.9 MiB), 가설 측정은 `small` 만. 조건마다 템플릿을 새 하위 디렉터리로 복사한다.
- **순서 효과**: 조건마다 버리는 워밍업 칸 하나, 그 뒤 블록(본 12·가설 6)마다 변형 순서를 무작위로 섞는다(시드 = 블록 번호, 두 환경 같은 순서). 칸은 본 1.5초·가설 1초 닫힌 루프다. 짝 차이는 같은 블록의 기준과 낸다.
- **실패 처리**: SQLite 오류(busy 등)는 칸의 `errors` 에 센다(재실행 모두 0건). 그 밖의 워커 예외는 칸을 `RuntimeError` 로 올려 실행을 멈춘다.
- **계측**: 처리량, 지연 p50·p99, `perconn` 계열 단계별 시간, 칸 끝 RSS. Linux 에서는 `sqlite3_status64` 의 MEMORY_USED·PAGECACHE_OVERFLOW(pcache 가 malloc 으로 받은 바이트)·MALLOC_COUNT(동시 생존 할당 수 — 총 호출 수가 아니다) 최고치. 요청당 minor fault 는 프로세스 전체 `getrusage` 다. macOS 의 uv Python 은 SQLite 를 정적으로 넣어 ctypes 로 같은 인스턴스에 닿지 않아(`CDLL(None)` 은 시스템 사본 3.51.0) RSS 만 남겼다.

이 경로가 말하는 것은 "상한을 올리면 상한에 닿을 때까지 재활용하지 않는다"이다. 캐시를 키운 연결이 같은 페이지를 다시 읽으면 그 버퍼는 이득이 되고(리뷰 1 반례, H3), 다시 읽지 않고 닫으면 할당·해제만 남는다(H1). 다른 연결의 쓰기는 다음 읽기 트랜잭션에서 캐시를 비우므로 재사용 연결도 다시 읽기 이득을 잃는다(H2). 이 소스가 임의의 요청에서 캐시 재사용이 불가능하다는 뜻은 아니다. 할당·해제마다 전역 mutex 두 개를 지나므로 스레드가 많으면 더 나빠질 수 있다 — 16 스레드에서 악화가 더 큰 것과 맞지만 경합을 재지 않았으므로 **추정**이다.

- **`sort10diff`(탐색적).** 연결 하나에서 다른 구간 정렬 10회는 환경에 따라 갈렸다: macOS +8.8%(1)·+40.2%(16), Linux −0.6%(1, 판정 불가)·−54.8%(16). Linux 1 스레드에서 pcache 할당 최고가 26.9 MiB 로 커지고 close 평균이 202 → 2,184µs 로 늘었다. 다시 읽는 페이지의 이득과 새 페이지 할당·해제 비용이 겹치는 경우로 보며, 어느 쪽이 큰지는 환경과 스레드 수에 달렸다(**추정**).

**관측(재현함, 원자료 재계산)**

- #10: `cache_size` 단독은 5회 모두 정렬 지연이 +21~+27% 로 읽기·쓰기(+6~+12%)보다 크게 늘었고, 정렬/읽기 비가 1.43–1.46(같은 반복 기준 1.25–1.28)이었다. `mmap_size` 단독과 '넷 다'(`all`)는 정렬이 −5~−11% 로 줄고 비가 1.14–1.16 이었다.

**해석(추정)**

- #10 의 '정렬만 더 느려짐, `all` 이면 사라짐'은 최소 재현의 기전(H1, 정렬 요청에서 `cache_size` 비용, `mmap_size` 와 함께면 사라짐)과 **일관된다**. 랩에서 원인별 기여를 통제하거나 계측한 것은 아니다.
- `cache_size`+`mmap_size` 두 설정만의 근거는 최소 재현뿐이다. 랩에는 그 변형이 없다(#10 은 네 개를 함께 켠 `all`, #26 에는 `all` 도 없다).
- #26 의 처리량 판정이 '재현 안 됨'이 된 것은 실행 사이 흔들림(기준 처리량 표준편차 약 7%)이 효과를 가렸다는 해석과 **일관된다**(추정). 반복 5 는 비율이 올랐지만 정렬 절대 지연은 거의 그대로이고 읽기·쓰기가 빨라진 것이라, 비율만으로 "정렬 쪽 비용은 그대로"였다거나 처리량 반전이 외부 소음 때문이라고 분리해 입증할 수 없다.
- 랩 악화(−8~−12%)가 최소 재현(−15~−80%)보다 작은 것은 랩 요청 하나에 Django·ASGI 비용이 더해지고(요청 지연 20ms 대, 최소 재현은 0.1ms 대) 정렬이 요청의 10% 뿐이기 때문으로 본다(추정, 재지 않음).

**새 랩 실행을 하지 않은 것과 그 한계**: 정렬 비율만 바꾼 단계나 `cache_mmap` 변형은 벤치 하네스(`lab/test_bench.py` 의 `PHASES`·`ALL_VARIANTS`)를 고쳐야 해서 돌리지 않았다. 그래서 랩 쪽 근거는 위의 관측(일관성)까지이고, 랩에서의 인과는 **미검증**이다.

### 문서·설정에 주는 것

- `database.py` 기본값은 바꾸지 않는다. `cache_size` 는 계속 '켜지 않음'이다.
- 안내는 측정 범위로 한정한다: 측정한 조건 중 연결당 요청 1~10개의 혼합 부하(인덱스 없는 정렬 10%), 연결 하나에서 많은 페이지를 한 번씩만 읽는 요청, 여러 연결이 쓰는 재사용 연결에서는 `cache_size` 상향이 처리량을 떨어뜨렸다. 한 연결(요청·트랜잭션) 안에서 같은 페이지를 다시 읽는 요청과 다른 연결의 쓰기가 없는 재사용 연결에서는 좋아졌다. 올리려면 자기 부하로 잰다.
- 제안(적용 안 함): `sqlite_doctor` 나 시스템 체크가 `CONN_MAX_AGE=0` 과 `cache_size` 상향을 함께 보면 알리는 것. 위처럼 부하에 따라 방향이 바뀌므로 경고 기준의 근거가 없어 이 이슈에서는 만들지 않는다.

## 미검증

- 16 스레드 악화에서 전역 mutex 경합의 기여(perf·lock 통계로 재지 않았다).
- 16 스레드 pk 읽기에서 `cache_size` 의 악화.
- C2 가 틀린 두 칸에서 `cache_size` 가 mmap 위에 더한 몫.
- 랩에서 정렬 비율·`cache_mmap` 을 바꾼 확인.
- 첫 실행에 워커 실패가 있었는지(당시 하네스는 검출하지 못했다).
- amd64, 다른 libc(musl)·할당기, SQLite 3.37.2(`sqlite-floor`) 같은 다른 판. 3.46.1 과 3.53.1 두 판에서만 쟀다.
- `sort10diff` 의 환경별 차이의 원인, 64 MiB 를 넘는 DB 에서의 `sort10*`, 큰 WAL(WAL 의 페이지는 mmap 으로 읽지 않는다)에서 `cache_mmap` 의 동작.
- Django 가 연결마다 등록하는 Python 함수(수십 개)의 비용.
