# PRAGMA 벤치 재측정 (2026-10-08, #26)

[#10 벤치](lab-2026-10-08.md#pragma-벤치)의 빈틈 세 가지를 다시 쟀다: `CONN_MAX_AGE=None`(연결 재사용) 조건, 측정 중에 WAL 이 실제로 자라는 부하, 병목 위치(#10 리뷰 1). 수치는 모두 아래 실행의 원자료에서 나왔다. 근거는 **재현함**(이 실행에서 다시 일어남)·**코드상 확인**(소스를 읽음)·**추정**(수치에서 미루어 봄)·**미검증**으로 나눠 적었다.

## 요약

- **`CONN_MAX_AGE=None` 은 ASGI 에서 연결을 재사용하지 않는다(재현함).** DB 요청당 연결 생성 수가 0 일 때와 같은 0.989–1.001 이다. 대신 연결이 바로 닫히지 않고 쌓여 DB 파일 디스크립터가 810–982개(소프트 한도 1024)까지 올라갔고, 그때 `OperationalError: unable to open database file` → HTTP 500 이 났다(벤치 40단계 중 4단계에서 216건, 포화 측정 동시 16·48 에서 64–827건). `CONN_MAX_AGE=0` 은 fd 37–42, 오류 0.
- **재현된 PRAGMA 차이는 없다**(두 `CONN_MAX_AGE` × 두 부하 단계 × 후보 셋). 이번 실행은 반복 간 흔들림이 커서(기준 처리량 표준편차 약 7%, #10 은 약 2%) 짝 차이가 ±20% 까지 오갔다. #27(`cache_size` 단독 악화)은 **이번에는 재현되지 않았다**: 혼합 부하 `CONN_MAX_AGE=0` 에서 −9.9, −9.8, −4.6, −15.0, **+19.0**%.
- **WAL 이 자라는 부하를 만들었다.** 쓰기 단계에서 WAL 이 씨앗 뒤 39.7 MB 에서 측정 중 최대 70.0–138.9 MB 까지 자랐고 최대값이 회차마다 달랐다. **`journal_size_limit`(64 MiB)은 WAL 크기를 묶지 못했다**: 그 변형에서만 WAL 이 정확히 67,108,864 B 로 잘린 일이 5번(10단계 중 4단계) 있었지만 곧 다시 자라 최대 79.6–124.4 MB 였다. 구조는 코드상 확인: SQLite 는 WAL 재시작 뒤 **첫 커밋을 한 연결**의 한도로만 자르고, Litestream 0.5.17 은 체크포인트 직후 자기 연결로 `_litestream_seq` 에 쓴다. 그 첫 커밋을 대개 Litestream 이 가져가서 드물게만 잘린다는 것은 추정이다(어느 연결이 커밋했는지 관측하지 않았다).
- **이 계측 조건에서 처리량이 포화했고 부하 발생기에는 여유가 있었다(실측). 앱 프로세스 CPU/GIL 병목이 의심되지만 원인은 미검증이다.** `CONN_MAX_AGE=0` 에서 동시 4→16→48 로 올려도 처리량이 늘지 않고(474–572 req/s), 서버 프로세스 CPU 는 1.33–1.45 코어로 일정하다. 발생기: 혼합 부하에서 CPU 0.07–0.09 코어, 같은 발생기로 Django 를 거치지 않는 경로는 10,000–12,800 req/s. CPU/GIL 대기·DB 잠금·I/O 대기·호스트 스케줄링을 나눠 잰 기록은 없다.
- 제안: `database.py` 기본값은 그대로 둔다. `CONN_MAX_AGE=None` 은 ASGI 동기 뷰에서 쓰지 말라고 문서에 적는다(이 PR 에서 README 함정에 추가). 자세한 것은 [제안](#제안).

**계측**(랩 앱만, 패키지 코드는 그대로)
- 연결 재사용: `connection_created` 시그널 횟수와 DB 를 쓰는 요청 수를 앱 프로세스에서 센다(`notes/metrics.py`). 측정 구간 처음·끝 표본의 차이로 "DB 요청당 연결 생성"을 낸다. 1 이면 재사용이 없다. 열린 DB 파일(본체·`-wal`·`-shm`) 디스크립터 수도 `/proc/self/fd` 로 센다.
- WAL: 0.5초마다 `/lab/probe`(DB 연결을 열지 않음)로 `-wal` 크기와 헤더의 체크포인트 순번(`ckpt_seq`)을 읽는다. 크기가 앞 표본보다 작아진 횟수를 '줄어듦'으로 센다. 크기 최대는 표본 최대다(연속 관측 아님). 이 실행은 측정 구간 처음·끝의 `ckpt_seq` 차이를 'WAL 재시작 횟수'로 기록했지만 **그 의미는 보증할 수 없다**: `ckpt_seq` 는 헤더를 쓴 연결 핸들의 카운터라, 여러 연결(요청마다 새 앱 연결과 Litestream)이 WAL 을 재시작하면 재시작 횟수가 아니다(#26 리뷰 1 재현: 두 연결이 번갈아 6번 재시작했는데 순번은 3 늘었다. SQLite 3.46.1 `wal.c` 의 `Wal.nCkpt`·`walRestartHdr` 로 구조 확인). 이 실행의 JSON 에는 시작·끝 헤더가 남아 있지 않아 다시 셀 수도 없다. 지금 코드는 시작·끝 헤더(`ckpt_seq`·salt 둘)를 남기고, 차이는 `wal_ckpt_seq_delta` 로, 표본 사이 salt 가 바뀐 횟수는 `wal_salt_changes`(그 사이 헤더가 한 번 이상 다시 쓰였다는 하한)로 낸다. 정확한 재시작 횟수를 세는 방법은 만들지 않았다(한계).
- 서버 시간: 응답 헤더 두 개. `X-Lab-Svc-Us`(이 실행, 아래 표의 'svc p50')는 첫 미들웨어 `notes.middleware.timing` 이 `get_response` 를 감싸 잰 시간이다. **순수 뷰 시간이 아니다**: ASGI 핸들러는 sync-only 미들웨어에 `async_to_sync(_get_response_async)` 를 넘기고 그 안에서 동기 뷰를 다시 `sync_to_async` 로 부르므로, 이벤트 루프 왕복과 뷰 스레드 배정 대기가 들어간다(#26 리뷰 1 재현: 핸들러에 50 ms 대기를 넣으면 뷰 0.1 ms 에 헤더 약 52 ms. Django 6.1.2 소스로 확인). 또 이 미들웨어는 배포 프로필에 없는 sync/async 왕복을 더한다(모든 변형에 같이 걸렸지만 그 비용이 변형마다 같은지는 미검증). `X-Lab-App-Us` 는 ASGI 래퍼에서 요청을 받은 때부터 응답 시작까지다. 서버 프로세스 CPU 시간(`time.process_time`)의 차이 / 경과 시간 = 서버 CPU(코어 수). 지금 코드는 미들웨어를 빼고 뷰 함수 호출만 감싸 `X-Lab-View-Us` 로 잰다(`notes/timing.py`, 같은 재현에서 헤더 0.148 ms). 같은 요청 안의 차이(클라이언트−앱, 앱−뷰)도 요청마다 계산해 분포로 남긴다.
- 발생기 여유: 발생기 프로세스 CPU / 경과 시간, 그리고 같은 발생기로 DB 없는 두 경로 — `ping`(Django 뷰, DB 없음)과 `rawping`(Django 앞 ASGI 래퍼가 바로 답함).
- 포화 측정(`test_saturation`, 반복 2, CMA 둘 다, 기준 설정): 부팅·씨앗 뒤 `rawping` 동시 16·48 → `ping` 16·48 → `mixed` 동시 4·16·48 을 각 2초 워밍업 + 10초.

**판정**(#10 과 같음): 같은 반복·같은 CMA·같은 단계의 기준과 짝지어 차이(%)를 내고, **5회 모두 같은 방향으로 5% 이상**이면 '재현'(`lab/_benchstat.py`, 단위 테스트 `tests/test_lab.py`). 이 실행의 코드는 차이를 소수 첫째 자리로 반올림한 뒤 판정했다(4.96% 가 5.0 으로 올라가 재현이 될 수 있었다, #26 리뷰 1). 지금은 반올림 전 값으로 판정하고 표시만 반올림한다. 이 실행의 24개 판정(아래)을 반올림 전 값으로 다시 판정해도 모두 '아니오'다(`.work/issue-26/rejudge-r1.txt`).

## 결과: 연결 재사용

| `CONN_MAX_AGE` | DB 요청당 연결 생성 | 측정 중 열린 DB fd 최대 | 500 오류 |
|---|---|---|---|
| `0` | 0.9992–1.0011 (40단계) | 37–42 | 0 |
| `None` | 0.9892–1.0007 (40단계) | **810–982** (한도 1024) | **216건**(4단계: `mixed` 의 mmap 4회차 26, cache 5회차 68, jsl 4·5회차 합 122) |

- **재사용 없음(재현함).** 두 값 모두 DB 요청 하나마다 연결이 새로 열렸다. 코드상 확인: Django 6.1.2 `ASGIHandler.__call__` 은 요청마다 `async with ThreadSensitiveContext()` 를 쓰고(`django/core/handlers/asgi.py`), asgiref 3.12 는 그 컨텍스트마다 스레드 하나짜리 실행기를 새로 만든다(`SyncToAsync.context_to_thread_executor`). DB 연결 저장소는 `thread_critical=True`(스레드 로컬)라, 요청마다 새 스레드 → 새 연결이다. 그래서 이 프로필(ASGI, 동기 뷰)에서는 `CONN_MAX_AGE=None` 이 연결 수명을 늘리지 못하고, `cache_size`·`mmap_size` 가 긴 연결에서 이득을 본다는 가정을 시험할 조건이 만들어지지 않는다.
- **`None` 은 연결을 쌓는다(재현함).** `0` 은 요청 끝(`request_finished`)에 연결을 닫지만 `None` 은 닫지 않는다. 끝난 스레드의 연결은 객체가 회수될 때까지 파일을 쥐고 있어(추정) 열린 DB fd 가 수백 개다.

### `CONN_MAX_AGE=None` 의 오류

- 본 실행 포화 1회차(`none`·`mixed`·동시 48, `saturation-20261008-234839.json` 에 남은 로그)에서는 `sqlite3/base.py:205` 의 `conn = Database.connect(**conn_params)` — **연결 생성 자체**에서 `django.db.utils.OperationalError: unable to open database file` 이 났다. 탐색 실행 2(`probe2.console`, 포화 `mixed` 동시 48)에서는 같은 메시지가 `get_new_connection` 의 `init_command` 실행 중에 났다. 그때 열린 DB fd 는 932–961, 한도 1024 다. **원인을 fd 고갈로 보는 것은 추정이다** — SQLite 메시지에 errno 가 없다.
- 본 실행 벤치의 4단계(216건)는 앱 로그 끝 6,000자만 남겨 예외 줄을 놓쳤다(모두 HTTP 500, 같은 단계의 fd 최대는 위 범위). 지금 코드는 전체 로그에서 예외 줄을 센다.
- 포화 측정의 오류: `None` 동시 16 에서 1회차 64건(2회차 0), 동시 48 에서 827·641건. `0` 은 0.

## 한계

- 반복 간 흔들림(기준 약 7%)이 판정 문턱(5%)보다 크다. 이 실행은 5% 크기의 PRAGMA 효과를 검출할 힘이 없다. 원인(계측 부하, 단계 연속 실행, 호스트의 다른 컨테이너)은 가리지 않았다.
- `temp_store` 와 '넷 다' 변형은 이번에 재지 않았다(시간 예산). #10 의 결과(재현 없음)가 그대로 근거다.
- `CONN_MAX_AGE=None` 의 `mixed` 4단계는 500 이 섞인 채로 처리량을 쟀다(오류 응답은 처리량에 넣지 않았다).
- 연결 재사용이 일어나지 않아 "긴 연결 수명에서 `cache_size`·`mmap_size`" 는 이 프로필로는 잴 수 없다. 재사용이 되는 조건(WSGI, 또는 async 뷰 + 연결 풀)은 다른 프로필이라 하지 않았다.
- `journal_size_limit` 이 드물게만 일하는 구조는 소스로 확인했고, 어느 연결이 재시작 뒤 첫 커밋을 했는지는 직접 관측하지 않았다. Litestream 없이 같은 부하를 거는 대조군은 돌리지 않았다.
- fd 고갈이 500 의 원인이라는 것은 수치에 근거한 추정이다(errno 미확인).
- 한 호스트(arm64 colima)에서 1회 실행이다.
- **WAL 재시작 횟수는 이 실행으로 알 수 없다.** 기록한 `ckpt_seq` 차이는 다중 연결에서 재시작 횟수도, 재시작이 있었다는 하한도 아니고, 시작·끝 헤더를 남기지 않아 다시 셀 수도 없다. 지금 코드의 `wal_salt_changes` 도 0.5초 표본 사이의 변화만 보는 하한이다. 모든 재시작을 세려면 연속 관측이 필요한데 만들지 않았다.
- **이 실행의 서버 시간 계측(`X-Lab-Svc-Us` 미들웨어)은 배포 프로필에 없는 sync/async 왕복을 더했다.** 모든 변형에 같이 걸렸지만 그 비용이 PRAGMA 차이를 가리는 정도는 재지 않았다. 계측을 끈 대조군도 없다(probe 의 fd 열거 비용도 같다). 기존 svc 수치는 그 옛 의미로만 인용한다.
- 병목 원인(앱 CPU/GIL)은 확정하지 않았다. 포화와 발생기 여유만 실측이다.

## 제안

`database.py` 는 바꾸지 않았다(오케스트레이터가 정한다).

1. **후보 넷 모두 계속 끔.** 이번에도 개선이 재현된 후보가 없다.
2. **`cache_size` 의 '켜지 않음' 근거는 #10 결과만 남긴다.** #10 에서는 5회 모두 나빠졌고, 이번에는 4회 나빠지고 1회 좋아져 재현되지 않았다. 근거 문구를 "#10 에서 반복해서 나빠짐, #26 에서는 재현 안 됨(소음 큼)"으로 바꾸고 원인은 #27 에서 본다.
3. **`journal_size_limit` 은 Litestream 과 함께 쓰면 WAL 크기를 묶지 못한다**는 것을 근거로 적는다(코드상 확인 + 관측: 10단계 중 4단계에서만 잘림, 최대는 기준과 같은 범위). WAL 크기를 묶어야 한다면 앱 PRAGMA 가 아니라 Litestream 쪽 설정(`truncate-page-n` 등)을 봐야 한다 — 이번엔 재지 않았다.
4. **`CONN_MAX_AGE=None` 을 ASGI 동기 뷰에서 쓰지 말라고 안내한다.** 재사용 이득은 없고 fd 를 쌓아 500 을 낸다(재현함). 이 PR 에서 README 문제 해결 표에 넣었다. 시스템 체크(ASGI + `CONN_MAX_AGE=None` 인 비 VFS 별칭에 경고)로 만들지는 따로 정할 일이다. VFS 별칭은 WSGI 에서 `None` 이 필수였는데(W003), ASGI 에서 VFS 가 어떻게 되는지는 여전히 미검증이다.
