# fd 한도를 올린 ASGI + `CONN_MAX_AGE` 장시간 실행 (2026-10-09, #33)

[#26](bench-2026-10-08.md#결과-연결-재사용)에서 ASGI 동기 뷰 + `CONN_MAX_AGE=None` 은 연결을 재사용하지 않고 닫지도 않아 열린 DB fd 가 810–982개(소프트 한도 1024)까지 쌓였고 `unable to open database file` 500 이 났다. 이번에는 **"fd 한도를 크게 올리면 수용되는가"** 를 물었다. 앱 컨테이너의 열린 파일 한도를 컨테이너가 허용하는 최대(1,048,576)로 올리고 메모리를 2 GiB 로 막은 뒤, `None` 과 `0` 을 같은 부하로 30분씩 돌렸다. 수치는 모두 아래 실행의 원자료에서 나왔다. 근거는 **재현함**(이 실행에서 일어남)·**추정**(수치에서 미루어 봄)·**미검증**으로 나눠 적었다.

## 요약

- **fd 한도를 올리면 이 조건(동시 16, 30분, 요청 118만 건)에서는 `None` 이 오류 없이 돌았다(재현함).** 오류 0, 조기 정지 없음, OOM 없음.
- **fd·RSS 는 요청 수에 비례해 계속 늘지 않고 일정 수준에서 멈췄다(재현함).** `None` 의 열린 fd 는 첫 10초에 885개로 올라선 뒤 30분 동안 882–1,531개(중앙값 1,250) 사이를 오갔다. 앱 RSS 는 첫 2분에 약 400 MiB 로 올라선 뒤 310–465 MiB(중앙값 411 MiB)에 머물렀다. 누적 DB 요청에 대한 fd 기울기는 요청 1만 건당 약 1개(r² 0.07)이고 뒤 절반은 앞 절반의 약 30%다. 누적이 아니라 흔들림이다. 닫히지 않은 연결은 시간이 지나면 회수된다(무엇이 회수하는지는 미검증 — 아래 [회수](#회수)).
- **비용은 남는다(재현함).** 5분 뒤 구간 평균으로 `None` 은 `0` 보다 fd 1,255 대 82, 앱 RSS 413 대 74 MiB, cgroup 메모리 610 대 333 MiB 다. 구간 p99 의 최대는 116 대 67 ms 다. 처리량은 655 대 681 req/s(평균)로 한 번씩만 돌려 차이를 말할 수 없다.
- **이득은 여전히 없다(재현함).** DB 요청당 연결 생성은 두 값 모두 1.0 이다(#26 과 같다).
- **열려 있는 연결 하나당 메모리는 약 250–420 KiB(추정).** RSS 를 DB 본체 fd 수에 회귀한 기울기가 248 KB(r² 0.40, 약함)이고, 두 실행의 평균 차이(RSS 차 ÷ DB 본체 fd 차)는 416 KiB 다.
- **한도에 닿는 예상 시간: 이 부하에서는 닿지 않는다(추정).** 뒤 절반의 시간 기울기가 fd +0.034개/초, RSS −15.7 KB/초로 0 근처라 외삽이 뜻이 없다(fd 한도까지 3,600만 초 같은 값이 나온다). 대신 #26 의 500 은 이 정상 상태 수준(fd 약 900–1,500)이 기본 한도 1024 를 넘기 때문이라고 보는 것이 맞다(추정, 같은 동시 16).
- 결론: **fd 한도를 올리면 `None` 의 500 은 이 부하에서는 사라지지만, 재사용 이득 없이 fd 약 15배·RSS 약 5.6배를 쓴다.** 권장은 그대로 `0`(또는 키 삭제)이다. W005 의 hint 는 이 결과와 모순되지 않아 고치지 않았다(아래 [W005](#w005-와의-관계)).

## 환경

- 호스트: macOS 26.6.2(Apple M1 Pro, 10코어) + colima 0.10.3 `default`(linux/arm64, 4 CPU, 8 GiB, 커널 6.8.0-117, cgroup v2). 같은 VM 에서 다른 프로젝트 컨테이너 20개가 돌았다(부하는 통제하지 않았다). 다른 colima VM(`bench`)도 켜져 있었다(쓰지 않음).
- Docker 29.5.2(클라이언트 29.8.1), Docker Compose 5.5.1.
- 앱 이미지 `dso-lab-app:3250e12`(`sha256:c90cc147…`, arm64) — 베이스 `python:3.13-slim@sha256:bf44cdfcb76cd3b41e879bc058fc37ec5872002ccfde7fcb765e218cde0cd79c`. 이미지 안: Python 3.13.16, Django 6.1.2, uvicorn 0.54.0(워커 1), asgiref 3.12.1, SQLite 3.46.1, Litestream 0.5.17. 배포 프로필(single-server) 그대로이고 Litestream 이 복제한다.
- **열린 파일 한도.** compose [`ulimits`](https://docs.docker.com/reference/compose-file/services/#ulimits) 로 `nofile` soft·hard 를 1,048,576 으로 줬다. 이 값은 VM 의 `/proc/sys/fs/nr_open`(1048576, 프로세스가 올릴 수 있는 최대)이다. 실제 적용값(원자료 `kind: env`, 두 실행 같음): 앱 프로세스(uvicorn, pid 36·37)의 `/proc/self/limits` 와 PID 1(`litestream replicate ...`)의 `/proc/1/limits` 가 모두 `Max open files 1048576 1048576`. `fs.file-max` 는 9223372036854775807(VM 전체 상한이 사실상 없음). 참고로 한도를 주지 않은 같은 VM 의 컨테이너는 soft 1024·hard 524288 이다.
- **메모리 한도.** compose [`mem_limit`](https://docs.docker.com/reference/compose-file/services/#mem_limit)·[`memswap_limit`](https://docs.docker.com/reference/compose-file/services/#memswap_limit) 을 같은 `2g` 로 줬다(같으면 스왑 없음). 실제: cgroup `memory.max` 2147483648, `memory.swap.max` 0. 실행 끝까지 `memory.events` 의 `max`·`oom`·`oom_kill` 은 0.
- **안전 정지 조건**(이번에는 걸리지 않음): 앱 RSS ≥ `memory.max` × 0.8, cgroup `oom_kill` ≥ 1, 오류율 ≥ 0.5 가 3구간(30초) 연속, 표본 3구간 연속 실패.

## 방법

- `CONN_MAX_AGE` 값마다 스택을 새로 띄워(`down -v` → `up`) 새 볼륨·새 복제본 prefix 로 `--init-new` 부팅 → `lab_seed` 로 행 100,000 → 5초 쉼 → 부하 직전 표본 → 부하 1,800초. 실제 값은 `/lab/soakenv` 의 `conn_max_age` 로 확인했다(`None`·`0`).
- 부하: `loadgen.py --report-every 10`. 닫힌 루프 스레드 16개, keep-alive. #26 벤치 `mixed` 와 같은 비율(읽기 70%·인덱스 없는 정렬 10%·1행 쓰기 20%). 두 값이 같은 부하·같은 시드다.
- 10초마다 한 줄: 그 구간의 처리량·p50·p99·오류(종류별), 누적 요청 수, 그리고 앱 프로세스 안 `/lab/soakprobe`(DB 를 열지 않음) 표본 — `/proc/self/fd` 의 readlink 로 나눈 fd(DB 본체·`-wal`·`-shm`·소켓·기타), `/proc/self/status` 의 `VmRSS`·`VmHWM`·`Threads`, Python 스레드 수, cgroup `memory.current`·`memory.events`, `gc` 세대별 수집 횟수, WAL 크기, 연결 생성·DB 요청 카운터.
- 분석은 `lab/_soakstat.py`(순수 함수, `tests/test_lab.py` 가 Docker 없이 검사). 기울기는 구간 표본에 맞춘 최소제곱 직선이다(추정).

- **멈춤(재현함).** `None` 의 DB 본체 fd 는 70초에 816 에 닿고, 590초에 833, 750초에 885 로 올라선 뒤 끝까지 885 다. `-wal` fd 는 34–652 사이를 오르내린다(늘었다가 줄어든다). fd 합계의 최대(1,531)는 1,590초에 나왔다. 처음 5분 뒤만 보면 fd 960–1,531, RSS 377–465 MiB 다. `_soakstat` 의 모양 판정은 fd 가 `slows`(뒤 절반 기울기가 앞의 30%), RSS 가 `plateau`(뒤 절반 기울기 음수)다.
- **`0` 도 DB 본체 fd 를 31–32개 쥐고 있다(재현함).** `0` 은 요청 끝에 연결을 닫는데도 본체 fd 가 동시 수(16)의 약 두 배로 일정하다. SQLite unix VFS 는 같은 inode 에 다른 연결의 POSIX 잠금이 남아 있으면 닫는 연결의 fd 를 바로 닫지 않고 미뤄 두었다가 다음 open 에 다시 쓰는데, 그것으로 보인다(추정, 소스·트레이스로 확인하지 않음).
- **열려 있는 연결 하나당 메모리(추정).** 두 방법으로 쟀다. (1) `None` 실행 안에서 RSS 를 DB 본체 fd 수에 회귀: 247,961 B/fd(r² 0.40, DB 본체 fd 범위 380). 본체 fd 가 계단 모양이라 회귀가 약하다. (2) 5분 뒤 구간 평균의 두 실행 차: RSS 412.9 − 73.5 MiB, DB 본체 fd 866.6 − 32.0 → 약 416 KiB/연결. 둘 다 SQLite 연결 하나(페이지 캐시·`-wal` 핸들)와 그 연결을 쥔 Django 연결 객체·스레드 잔여물을 합친 값이다. 무엇이 얼마인지는 나누지 않았다.
- **한도에 닿는 예상 시간(추정).** 뒤 절반 기울기로 외삽하면 fd 한도 1,048,576 까지 31,224,719초(약 361일), RSS 는 줄고 있어 메모리 한도 도달 시간이 없다(`eta_mem_limit_s_est` = null). 기울기가 흔들림 수준이라 이 숫자는 "이 부하에서는 늘지 않는다" 이상의 뜻이 없다. 이 부하에서 실제로 닿는 것은 정상 상태 수준이다: fd 약 900–1,500 은 기본 소프트 한도 1024 를 넘는다. #26 의 500(같은 동시 16 에서 810–982개 근처)은 이 수준이 1024 를 넘나들어 났다고 보는 것이 수치와 맞다(추정, #26 에서도 errno 는 확인하지 못했다).

### 회수

닫히지 않은 연결이 쌓이기만 하지 않고 줄어드는 것은 재현했다(`-wal` fd·fd 합계·RSS 가 오르내림). 무엇이 회수하는지는 **미검증**이다. 후보는 요청마다 만들어졌다 끝나는 스레드와 그 컨텍스트가 사라질 때 Django 연결 객체가 참조를 잃고(참조 카운트 또는 순환 GC) `sqlite3.Connection` 이 닫히는 경로다. `gc` 세대 2 수집이 30분에 274번 일어났지만, 회수 시점과 맞춰 보지 않았다. 정상 상태 수준이 동시 수·요청 속도·GC 주기에 따라 어떻게 바뀌는지도 재지 않았다.

### 측정 비용

`/lab/soakprobe` 의 fd 열거는 앱 프로세스 안에서 돈다. `None` 에서 최대 248 ms(10초마다 한 번), `0` 에서 최대 24 ms 다. 이 시간 동안 GIL 을 쥐므로 `None` 의 지연(p99 최대 116 ms 등)에는 측정 자신의 비용이 섞여 있다. 그 몫은 나누지 않았다. 표본 응답 시간 최대: `None` 292.6 ms, `0` 68.6 ms.

## W005 와의 관계

[W005](../DESIGN.md#6-1-정적-체크-managepy-check-db-를-열지-않음) hint 는 "연결이 재사용되지 않고 요청 끝에 닫히지 않는다, 벤치에서 열린 DB fd 810–982(한도 1024)와 `unable to open database file`(fd 고갈은 추정 원인), `0` 으로 하거나 키를 지워라" 다. 이번 결과는 이 문장과 모순되지 않는다: 재사용 없음(연결 생성 1.0/요청)과 요청 끝에 닫히지 않음(fd 가 `0` 의 15배)을 다시 재현했다. 그래서 hint 는 고치지 않았다. 더한 사실은 문서(DESIGN §6-1 근거, README 문제 해결)에만 적었다: fd 한도를 올리면 이 부하에서는 오류 없이 멈춘 수준에서 돌지만 fd·메모리를 몇 배 쓰고 이득이 없다.

## 미검증

- 동시 16 하나만 쟀다. 동시 수(#26 의 48)·요청 속도·뷰 지연이 바뀔 때 정상 상태 수준(fd·RSS)이 어떻게 바뀌는지, 메모리 한도에 닿을 수 있는지.
- 30분보다 긴 실행, 부하가 멈춘 뒤 fd·RSS 가 어디까지 내려가는지.
- 회수의 메커니즘(위 [회수](#회수)). `0` 의 DB 본체 fd 31–32개가 SQLite 의 미룬 close 인지.

- 양수 `CONN_MAX_AGE`, VFS 별칭, 워커 둘 이상(multiproc), amd64.
