# fd 한도를 올린 ASGI + `CONN_MAX_AGE` 장시간 실행 (2026-10-09, #33)

[#26](bench-2026-10-08.md#결과-연결-재사용)에서 ASGI 동기 뷰 + `CONN_MAX_AGE=None` 은 연결을 재사용하지 않고 닫지도 않아 열린 DB fd 가 810–982개(소프트 한도 1024)까지 쌓였고 `unable to open database file` 500 이 났다. 이번에는 **"fd 한도를 크게 올리면 수용되는가"** 를 물었다. 앱 컨테이너의 열린 파일 한도를 컨테이너가 허용하는 최대(1,048,576)로 올리고 메모리를 2 GiB 로 막은 뒤, `None` 과 `0` 을 같은 부하 설정으로 30분씩 돌렸다. 수치는 모두 아래 한 실행(`soak-20261009-141051`)의 원자료에서 나왔고, 표는 `lab/soak_report.py` 가 원자료에서 만든 출력을 그대로 넣었다. 근거는 **재현함**(이 실행에서 일어남)·**코드상 확인**·**추정**(수치에서 미루어 봄)·**미검증**으로 나눠 적었다.

## 요약

- **fd 한도를 올리면 이 조건(동시 16, 30분)에서는 `None` 이 오류 없이 돌았다(재현함).** 요청 1,194,162건(측정 끝에 진행 중이던 꼬리 16건 포함), 오류 0, 조기 정지 없음, OOM 이벤트 0. 서버가 센 DB 요청 증가와 클라이언트가 센 요청 수가 정확히 같다(차 0).
- **관찰한 30분 동안 fd·RSS 는 요청 수에 비례해 늘지 않았다(재현함, 이 기간 안에서만).** `None` 의 열린 fd 는 첫 10초에 871개로 올라선 뒤 871–1,761개(중앙값 1,370) 사이를 오갔다. 앱 RSS 는 337–463 MiB(중앙값 411.5 MiB)에 머물렀다. 누적 DB 요청에 대한 DB 파일 fd 기울기는 요청 1만 건당 약 0.9개(r² 0.05)이고 뒤 절반은 앞 절반의 절반 아래다. RSS 의 뒤 절반 기울기는 음수다. 더 긴 시간의 정상 상태나, 열린 연결이 실제로 몇 개인지는 이 실행으로 말할 수 없다.
- **비용은 남는다(재현함).** 300초 뒤 구간 평균으로 `None` 은 `0` 보다 fd 1,363.0 대 81.4(16.75배), 앱 RSS 413.2 대 73.6 MiB(5.62배), cgroup 메모리 612.3 대 341.2 MiB 다. 구간 p99 의 중앙값은 46.77 대 42.61 ms, 최대는 70.224 대 58.706 ms 다. 처리량은 663.4 대 675.2 req/s(평균)로 한 번씩만 돌려 차이를 말할 수 없다.
- **부하가 멈추면 `0` 은 DB fd 를 모두 놓고 `None` 은 쥐고 있다(재현함, 끝 두 표본).** 측정이 끝난 순간과 꼬리 표본에서 `0` 은 DB 본체 fd 1 → 0, `None` 은 DB 본체 996·`-wal` 215 그대로다.
- **이득은 여전히 없다(재현함).** DB 요청당 연결 생성은 두 값 모두 1.0 이다(#26 과 같다).
- **열려 있는 연결 하나당 메모리는 약 370 KiB(추정, 약함).** 두 실행의 300초 뒤 평균 차(RSS 차 ÷ DB 본체 fd 차)가 369.8 KiB 다. `None` 실행 안에서 RSS 를 DB 본체 fd 수에 회귀하면 102,417 B 이지만 r² 0.0965 로 설명력이 거의 없다. DB 본체 fd 가 계단 모양(667 → 696 → 927 → 996)이라 회귀할 변화가 적다.
- **한도에 닿는 예상 시간: 이 부하에서는 외삽할 기울기가 없다(추정).** 뒤 절반의 시간 기울기는 fd +0.023개/초, RSS −10,342.5 B/초다. fd 한도까지 외삽하면 45,870,770초(약 531일)가 나오지만 흔들림 수준의 기울기라 뜻이 없고, RSS 는 줄고 있어 메모리 한도까지의 값이 없다. 대신 이 부하의 정상 상태 수준(fd 약 870–1,760)이 기본 소프트 한도 1024 를 넘는다. #26 의 500 은 이 때문이라고 보는 것이 수치와 맞다(추정, 같은 동시 16).
- 결론: **fd 한도를 올리면 이 부하에서는 `None` 의 500 이 사라지지만, 재사용 이득 없이 fd 약 17배·RSS 약 5.6배를 쓴다.** 권장은 그대로 `0`(또는 키 삭제)이다. W005 hint 는 이 결과와 모순되지 않아 고치지 않았다(아래 [W005](#w005-와의-관계)).

## 방법

- `CONN_MAX_AGE` 값마다 스택을 새로 띄워(`down -v` → `up`) 새 볼륨·새 복제본 prefix 로 `--init-new` 부팅 → `lab_seed` 로 행 100,000 → 5초 쉼 → 부하 직전 표본 → 부하 1,800초. 실제 값은 `/lab/soakenv` 의 `conn_max_age` 로 확인했다(`None`·`0`).
- 부하: `loadgen.py --report-every 10`. 닫힌 루프 스레드 16개, keep-alive. #26 벤치 `mixed` 와 같은 비율(읽기 70%·인덱스 없는 정렬 10%·1행 쓰기 20%). 두 값에 같은 동시 수·비율·시드·길이를 줬다. 닫힌 루프라 도착률·총 요청 수는 같지 않다.
- 10초마다 한 줄: 그 구간의 처리량·p50·p99·오류(종류별), 누적 요청 수, 그리고 앱 프로세스 안 `/lab/soakprobe`(DB 를 열지 않음) 표본 — `/proc/self/fd` 의 readlink 로 나눈 fd(DB 본체·`-wal`·`-shm`·소켓·기타), `/proc/self/status` 의 `VmRSS`·`VmHWM`·`Threads`, Python 스레드 수, cgroup `memory.current`·`memory.events`, `gc` 세대별 수집 횟수, WAL 크기, 연결 생성·DB 요청 카운터.
- 1,800초에 마지막 구간을 떼고 워커를 기다린 뒤, 그 사이 끝난 요청(워커마다 하나, 16건)을 꼬리 줄 하나로 남겼다. 꼬리는 누적 요청·오류에 넣고 구간 지표(처리량·p99)·분포·기울기에서는 뺐다. 1,800초 구간 표본은 워커가 멈추는 순간에 떴다(스레드·소켓 수가 줄어 있다).
- 분석은 `lab/_soakstat.py`(순수 함수, `tests/test_lab.py` 가 Docker 없이 검사). 기울기는 구간 표본에 맞춘 최소제곱 직선이다(추정). 중앙값은 `statistics.median`(짝수 개면 가운데 두 값의 평균), p90 은 최근접 순위법(정렬한 180개 중 `ceil(0.9 × 180)` = 162번째)이다.

### 두 실행 비교 (300초 뒤 평균, 추정 포함)

- fd 합계 비 16.75, RSS 비 5.62

### DB 본체 fd 가 바뀐 구간

- none: 10s→667, 20s→696, 40s→927, 830s→996
- 0: 10s→30, 80s→31, 520s→32, 1800s→1, 1800.02s→0(꼬리)

- **관찰 기간 안의 멈춤(재현함).** `None` 의 DB 본체 fd 는 40초에 927, 830초에 996 으로 올라선 뒤 끝까지 996 이다. `-wal` fd 는 64–802 사이를 오르내린다(늘었다가 줄어든다). OS 스레드는 중앙값 36 이지만 한 표본에서 396 까지 튀었다(그 순간 무엇이 스레드를 늘렸는지는 미검증). `_soakstat` 의 모양 판정은 DB 파일 fd 가 `slows`(뒤 절반 기울기가 앞의 절반 아래), RSS 가 `plateau`(뒤 절반 기울기 음수)다. 30분 뒤에도 같은지는 미검증이다.
- **`0` 도 부하 중에는 DB 본체 fd 를 30–32개 쥐고 있다(재현함).** `0` 은 요청 끝에 연결을 닫는데도 부하 중 본체 fd 가 동시 수(16)의 약 두 배로 일정하고, 부하가 끝나자 1 → 0 이 됐다. SQLite unix VFS 는 같은 파일에 다른 연결의 POSIX 잠금이 남아 있으면 닫는 연결의 fd 를 바로 닫지 않고 미뤄 두었다가 다음 open 에 다시 쓰는데, 그것으로 보인다(추정, 소스·트레이스로 확인하지 않음).
- **열려 있는 연결 하나당 메모리(추정).** 위 비교의 평균 차 369.8 KiB 와 `None` 안의 회귀 102,417 B(r² 0.0965)는 크게 다르다. 회귀는 본체 fd 가 네 번만 바뀌어 설명력이 없으므로 평균 차를 쓴다. 이 값은 DB 본체 fd 수를 열린 연결 수의 대리값으로 쓴 것이고, SQLite 연결(페이지 캐시·`-wal` 핸들)과 Django 연결 객체·스레드 잔여물을 합친 것이다. 무엇이 얼마인지는 나누지 않았다.
- **한도에 닿는 예상 시간(추정).** 위 표의 외삽값은 기울기가 흔들림 수준이라 "이 부하·이 기간에서는 늘지 않는다" 이상의 뜻이 없다. 이 부하에서 실제로 문제가 되는 것은 정상 상태 수준이다: fd 약 870–1,760 은 기본 소프트 한도 1024 를 넘는다. #26 의 500(같은 동시 16 에서 810–982개 근처)은 이 수준이 1024 를 넘나들어 났다고 보는 것이 수치와 맞다(추정, #26 에서도 errno 는 확인하지 못했다).

### 회수

닫히지 않은 연결이 쌓이기만 하지 않고 줄어드는 것은 재현했다(`-wal` fd·fd 합계·RSS 가 오르내림). 무엇이 회수하는지는 **미검증**이다. 후보는 요청마다 만들어졌다 끝나는 스레드와 그 컨텍스트가 사라질 때 Django 연결 객체가 참조를 잃고(참조 카운트 또는 순환 GC) `sqlite3.Connection` 이 닫히는 경로다. `gc` 세대 2 수집이 30분에 275번 일어났지만, 회수 시점과 맞춰 보지 않았다. DB 본체 fd 996개가 부하가 끝난 뒤에도 남은 것은 회수가 본체 fd 까지 닿지 않는 경우가 있다는 뜻일 수 있다(미검증). 정상 상태 수준이 동시 수·요청 속도·GC 주기에 따라 어떻게 바뀌는지도 재지 않았다.

### 측정 비용

`/lab/soakprobe` 는 앱 프로세스 안에서 `/proc/self/fd` 를 열거한다. `scan_ms` 는 그 열거의 경과 시간(`perf_counter`)이고 `None` 에서 최대 166.5 ms, `0` 에서 최대 32.1 ms 다. 경과 시간이므로 열거 자신의 비용과 함께 계측 스레드가 다른 스레드 때문에 기다린 시간도 들어갈 수 있다. CPython 3.13.16 은 `os.readlink()` 의 시스템 호출 동안 GIL 을 놓으므로([`os_readlink_impl`](https://github.com/python/cpython/blob/v3.13.16/Modules/posixmodule.c#L10348-L10359) 의 `Py_BEGIN_ALLOW_THREADS`·`Py_END_ALLOW_THREADS`, 코드상 확인) 이 시간 내내 GIL 을 쥐는 것은 아니다. 계측이 부하와 GIL 을 다투어 지연을 늘릴 수는 있지만 그 몫(예: `None` 의 p99)은 **미검증**이다 — 계측을 끈 대조 실행이나 프로세스 밖 계측이 필요하다.

## W005 와의 관계

[W005](../DESIGN.md#6-1-정적-체크-managepy-check-db-를-열지-않음) hint 는 "연결이 재사용되지 않고 요청 끝에 닫히지 않는다, 벤치에서 열린 DB fd 810–982(한도 1024)와 `unable to open database file`(fd 고갈은 추정 원인), `0` 으로 하거나 키를 지워라" 다. 이번 결과는 이 문장과 모순되지 않는다: 재사용 없음(연결 생성 1.0/요청)과 요청 끝에 닫히지 않음(fd 가 `0` 의 약 17배, 부하가 끝나도 남음)을 다시 재현했다. 그래서 hint 는 고치지 않았다. 더한 사실은 문서(DESIGN §6-1 근거, README 문제 해결)에만 적었다: fd 한도를 올리면 이 부하에서는 오류 없이 돌지만 fd·메모리를 몇 배 쓰고 이득이 없다.

## 미검증

- 동시 16 하나만 쟀다. 동시 수(#26 의 48)·요청 속도·뷰 지연이 바뀔 때 정상 상태 수준(fd·RSS)이 어떻게 바뀌는지, 메모리 한도에 닿을 수 있는지.
- 30분보다 긴 실행, 부하가 멈춘 뒤 시간이 지나면 `None` 의 fd·RSS 가 어디까지 내려가는지(끝 표본 두 개만 봤다).
- 회수의 메커니즘(위 [회수](#회수)). `0` 의 DB 본체 fd 30–32개가 SQLite 의 미룬 close 인지. `None` 의 OS 스레드 396 표본의 원인.
- 계측(fd 열거)이 지연에 더한 몫.
- 각 값 한 번씩만 돌렸고 순서는 `none` → `0` 고정이다. 처리량 차(663.4 대 675.2 req/s)와 p99 차는 이 실행만으로 말할 수 없다.
- 양수 `CONN_MAX_AGE`, VFS 별칭, 워커 둘 이상(multiproc), amd64.
