# Django 기본 SQLite 대 `sqlite_database()` 권장 설정 (2026-10-26, #83)

Django 의 기본 SQLite 설정과 이 패키지의 권장 설정(`sqlite_database()`)을 같은 하네스·같은 부하·같은 머신에서 번갈아 돌려 비교했다. 동시 쓰기가 들어간 부하에서 `database is locked` 오류 수, 처리량, p99 를 쟀다. 수치는 모두 아래 한 실행(`dbconfig-20261026-123720`)의 원자료에서 나왔다. 표는 `lab/dbconfig_report.py` 출력을 그대로 넣었다. 근거는 **재현함**(이 실행에서 일어남), **코드상 확인**, **추정**, **미검증**으로 나눠 적었다.

## 요약

- **Litestream 을 붙이면 Django 기본 설정도 WAL 로 돈다(재현함).** 프로필 그대로의 스택(boot → `litestream replicate`)에 Django 기본 설정을 넣었다. 그러자 `journal_mode` 가 `wal` 이었고 `transaction_mode` 는 없었다(DEFERRED). 그래서 비교는 boot·Litestream 없이 `migrate` → `uvicorn` 만 띄운 앱으로 했다.
- **읽고-고쳐-쓰기 트랜잭션에서 Django 기본은 `database is locked` 를 냈다. 권장 설정은 0 이었다(재현함, 10/10 실행).**
  - 부하: `transaction.atomic()` 안에서 `get` → `save`.
  - 기본 설정은 20초 단계마다 1,627–4,018건의 HTTP 500 을 냈다. `rmw` 요청의 42.9–47.9% 다.
  - 권장 설정은 모든 반복에서 0건이다.
  - 앱 로그의 `database is locked` 줄 수는 500 수와 정확히 같았다. 다른 예외 줄은 없었다.
- **단독 INSERT 만 있는 부하에서는 두 설정 모두 locked 0 이다(재현함).** 단독 INSERT 는 autocommit 이다(`mixed`·`write`). 기대대로 busy 대기(5초)가 흡수했다.
- **쓰기가 많은 부하에서 권장 설정의 처리량이 높고 p99 가 낮다(재현함, 5회 모두 같은 방향 5% 이상).**
  - `write` 단계(읽기 30%·50행 INSERT 70%), 워커 1: 처리량 +64–133%, p99 −48–62%.
  - `write` 단계, 워커 4: 처리량 +116–885%, p99 −77–93%.
- **읽기 위주 부하(`mixed`):**
  - 워커 4: 처리량 +61–91%, p99 −83–86%(재현함).
  - 워커 1: p99 는 −57–75% 로 재현했다. 처리량은 −12.5 – +15.9% 로 차이가 재현되지 않았다.
  - 워커 1 은 앱 프로세스의 CPU/GIL 이 먼저 막는 조건으로 보인다(#26 과 같은 추정, 원인은 미검증).
- **기대와 다른 것: 워커 1 의 `rmw` p99 는 권장 설정이 높았다(재현함, +36–144%).**
  - 기본 설정에서는 다툼에 걸린 요청의 약 46% 가 대기 없이 바로 실패했다. p99 는 성공한 요청만 센다.
  - 권장 설정(IMMEDIATE)은 같은 요청을 실패시키지 않고 쓰기 잠금을 기다리게 한다.
  - 오류가 대기로 바뀐 것이다. 워커 4 의 `rmw` p99 는 차이가 재현되지 않았다(−34 – +3%).
- **p50 은 `mixed` 에서 권장 설정이 높았다.** 워커 1 은 17.0 → 22.6 ms, 워커 4 는 6.3 → 9.8 ms 다.
  - 닫힌 루프라 처리량이 오르면 같은 동시 수에서 평균 지연이 줄어든다(워커 4: 16/822 ≈ 19.5 ms → 16/1,473 ≈ 10.9 ms).
  - 기본 설정은 빠른 요청과 아주 느린 꼬리로 나뉘었다. 분포 모양은 이 문서의 표 밖이다(추정).
- 제안: README 앞쪽 '왜 쓰는가'에 locked 0·쓰기 부하 처리량·p99 를 근거로 적는다. `rmw` 워커 1 의 p99 역전과 워커 1 `mixed` 처리량 무차이도 함께 적는다. `database.py` 기본값은 바꾸지 않는다.

### 왜 기본 설정에서 locked 가 나는가

이 실행은 원인을 관측하지 않았다. 다음은 SQLite 문서로 설명한 것이다(미검증: 어느 경로로 났는지 로그에 없다).
- [`sqlite3_busy_handler`](https://www.sqlite.org/c3ref/busy_handler.html) 문서(2026-10-26 확인)는 교착이 될 수 있으면 busy 핸들러를 부르지 않고 바로 `SQLITE_BUSY` 를 낸다고 한다. 문서의 예는 읽기 잠금을 쓰기 예약(reserved) 잠금으로 올리려는 연결과, 예약 잠금을 쥐고 배타 잠금으로 올리려는 연결이 만나는 경우다. 앞의 연결이 바로 `SQLITE_BUSY` 를 받는다. DEFERRED 트랜잭션의 `get` → `save` 가 그 '앞의 연결'이 된다.
- WAL 에서는 읽기로 시작한 트랜잭션이 쓰기로 올라갈 때 스냅샷이 낡았으면 `SQLITE_BUSY_SNAPSHOT` 이다(이 실행의 기본 설정은 rollback journal 이다).
- 그래서 busy 대기 시간을 늘려도 이 오류는 줄지 않는다고 본다(추정, 시험하지 않았다).
- IMMEDIATE 는 BEGIN 에서 쓰기 잠금을 잡으므로 다툼이 busy 대기로 들어간다. 이 실행에서 권장 설정의 locked 는 0 이었다.

  - 5회차(12:58–13:02)에 권장 설정의 처리량이 두 워커 모두 크게 낮았다: 워커 1 `rmw` 363.6, 워커 4 `write` 535.0·`rmw` 815.9.
  - 4회차 워커 4 기본 `write`(97.7 req/s, p99 2,025 ms)도 튀었다.
  - 원인은 관측하지 않았다. 워커 1 `rmw` 처리량이 '재현 안 됨'이 된 것은 5회차 +0.1% 하나 때문이다.
- Litestream 이 없는 앱이다. 운영 프로필은 Litestream 이 WAL 을 강제하므로 기본 설정을 그대로 쓰는 경우와 다르다.
  - 이 패키지 없이 Litestream 만 쓰는 배포는 WAL + DEFERRED 다. 그 조합은 재지 않았다.
  - 그 조합의 `rmw` 는 `SQLITE_BUSY_SNAPSHOT` 으로 실패할 수 있다(추정).
- 뷰는 랩 앱의 것이다. 실제 앱의 트랜잭션 모양에 따라 locked 비율은 달라진다.
- `synchronous`(FULL → NORMAL)와 journal mode·트랜잭션 모드의 효과를 나누지 않았다. 권장 설정 묶음 전체와 Django 기본을 비교했다.
- 지연 분포는 p50·p99 만 남겼다. 실패한 요청의 지연은 셈에 없다.
